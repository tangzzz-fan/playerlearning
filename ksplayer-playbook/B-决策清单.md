# B · 决策清单：十几个岔路口，以及每个路口的判据

> **结论先说**
>
> 播放器项目里**真正难的只有十几个决策**，其余都是执行。
> 而每个决策都有**判据**（"什么情况下选哪个"）—— 判据比结论更值得抄，
> 因为你的约束和我们的不一样，但**判断方法可以一样**。
>
> 下表每个岔路口都列三样：**判据 · 我们的选择 · 参考实现的选择**。
> 两者不同**不代表谁错** —— 参考实现是**产品**（要卖框架），我们是**自用 + 上架**。

---

## 一、总览（12 个岔路口）

| # | 岔路口 | 我们的选择 | 参考实现的选择 | 判据的关键是什么 |
| --- | --- | --- | --- | --- |
| 1 | **定位** | 自用为主，**目标上架** | 框架 + 商业 App（引流） | 是否分发 ⇒ **决定全部合规义务** |
| 2 | **内容范围** | 本地 + 网络点播 + 直播，**全都要** | 全都要 + 更多（DRM / 全景…） | "全都要"必须靠**第一期范围**钉住 |
| 3 | **平台顺序** | iOS 优先 → macOS 跟进 | 全平台同时（含 tvOS / visionOS） | **先啃最难的**（能跑通 iOS，别的容易） |
| 4 | **内核** | **单内核**（libmpv） | **双内核**（系统播放器 + 自研管线） | 是否有"只有某内核才有的能力"是刚需 |
| 5 | **产物来源** | **自建**（动态 + LGPL） | 用第三方产物（GPL） | **动态 + 宽松许可**能不能同时满足 |
| 6 | **抽象时机** | **第一天立边界**，只实现一个内核 | 边做边加（后来才引入第三个内核） | 扩展点成本 ≈ 0 时，**先立** |
| 7 | **渲染接入** | `wid` 嵌入（抽成协议） | `wid` 嵌入 | 是否要**处理每一帧**（要 ⇒ render API） |
| 8 | **工程骨架** | SPM 双 target + 生成式工程 | SPM 多 target + 二进制核心 | 内核能否**编译期隔离** |
| 9 | **UI 套数** | **一套**（跨平台） | 三套（UIKit / AppKit / SwiftUI） | 一套能覆盖就别写三套 |
| 10 | **测试边界** | 假内核 + 纯逻辑单测 | **近乎为零** | 无 I/O 才跑得快 ⇒ 变异测试才成立 |
| 11 | **依赖管理** | SPM `package(path:)` + 产物不入库 | 也走 SPM（**submodule 已删**） | 大二进制**永不入 git** |
| 12 | **门禁策略** | **不堆脚本**：验收 = 能跑 + 测试全绿 | CI 残缺 | 任何"每轮都要跑"的检查，成本落在每一轮 |

## 二、四个最关键的岔路口（展开）

### ① 内核：单内核 还是 双内核

**判据**：**是否存在"只有某个内核才有、且是刚需"的能力？**

| 如果 | 那么 |
| --- | --- |
| 你需要 DRM / AirPlay / 原生画中画 / 系统 HDR（如做在线视频 App） | ⇒ **双内核**（系统播放器兜这些，自研管线兜格式） |
| 你的核心价值是"什么格式都能播"、"要处理每一帧"（如播放器工具 / 3D 显示） | ⇒ **单内核**足够，把省下的成本投在那一个内核上 |

**我们选单内核**（libmpv）：因为"全格式 + 本地文件 + 要能拿帧"是核心价值，
而 DRM / AirPlay 我们用不到 —— 并且**把这些"用不到"显式写进放弃清单**（见 [`D`](D-产物与授权.md) §6）。

**参考实现选双内核**：它要卖的是**框架**，能力面必须**取并集**（它能跑流媒体 DRM，也能跑 mkv）。
代价是它必须同时维护两套解码路径。

> 🎯 **可迁移**：**别问"哪个内核好"，问"哪条能力是刚需"**。
> 详见 [`C-三种内核`](C-三种内核.md)。

### ② 抽象：第一天立 还是 边做边加

**判据**：**这个扩展点将来加一条腿的成本，现在立它要多少？**

参考实现给了**最强的证据**：它的第三个内核（libmpv）是**很久之后**才加进来的 ——
而当时往注册表里塞一条，**上层一行没改**。

| 做法 | 现在成本 | 将来加腿成本 |
| --- | --- | --- |
| 第一天立协议 + 只实现一个 | ≈ 0（一个协议 + 一个实现） | O(新实现) |
| 直接把内核 API 铺到 UI | 0 | **O(重构)** |

⇒ **抽象要早，实现要晚。**

### ③ 渲染接入：`wid` 嵌入 还是 render API

**判据**：**你需要"每一帧"吗？**

| 需求 | 选 |
| --- | --- |
| 只要能播、能看（字幕/色调映射/缩放都交给内核） | **`wid` 嵌入** —— 约 20 行，零渲染代码 |
| 要处理每一帧（滤镜 / 2D→3D / AI / 与自家 UI 合成） | **render API** —— 帧交给你，渲染循环你自己管 |

**我们第一期选 `wid`**，但**把"视频输出"收在协议后面** —— 将来要拿帧，只换一个实现。
（这条分界线的展开见 [`../knowledge/K6`](../knowledge/K6-浏览器在线视频-怎么变成可处理的帧.md) §3。）

### ④ 产物与许可：这是唯一"一开始就必须想清"的外部约束

**判据**：**你要不要分发？**（不分发 ⇒ 零义务；一旦分发 ⇒ 全部义务立刻生效）

| 若分发，则必须 | 为什么 |
| --- | --- |
| 产物是 **LGPL 构建**（不是 GPL） | GPL 会传染整个 App ⇒ 商店实质不可行 |
| 产物是 **动态链接** | 静态 ⇒ LGPL 要求"可重新链接"⇒ 等于要开源你的 App |
| 准备好**对应源码 + 许可文本** | LGPL 的分发要求 |

⇒ 展开见 [`D-产物与授权`](D-产物与授权.md)。

## 三、几个"小但会疼很久"的决策

| 岔路口 | 判据 | 建议 |
| --- | --- | --- |
| **时间推送粒度** | UI 每秒重绘几次会卡？ | **0.2–1 s 粒度**，不要毫秒级推 `@Published`（参考实现在代码注释里自己警告过这件事） |
| **素材来源** | 你的断言会不会因为"样例变了"而红？ | 用**真实视频**、运行时获取、参数别写死在断言里 |
| **平台差异放哪** | 这段差异是"逻辑"还是"翻译"？ | **逻辑进内核（可测），平台翻译留薄薄一层** |
| **版本控制什么** | 这个东西能重建吗？ | **能重建的（产物）不入库，重建方式（脚本 + 补丁）入库** |
| **文档交付形态** | 这个复杂度能用文字讲清吗？ | 讲不清就用**图 + 表**；只能实测的就写在**代码旁边** |

## 四、这张表的用法

> **别照抄结论，照抄"判据那一列"。**
>
> 你会发现：**上表 12 个岔路口里，只有「渲染接入」那一行给出了完全一样的答案**（两边都用 `wid` 嵌入），
> 其余或结论不同、或范围不同 —— **但两边的判断方法是一样的** ——
> 都是先问"我的刚需是什么"，再问"这个选择的成本落在谁身上、落在什么时候"。
