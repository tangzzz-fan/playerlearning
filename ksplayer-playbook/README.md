# ksplayer-playbook/ · 从零做一个"类 KSPlayer"的播放器项目

> **这份 playbook 回答的是**：如果现在要从零做一个自己的播放器项目（目标与形态和 KSPlayer 类似），
> **该按什么顺序做、在每个岔路口怎么选、每一阶段凭什么算过关。**
>
> 它**不是教程**，是**路线与决策** —— 教程讲"这行代码什么意思"，它讲"这一步为什么现在做、不这么做会付什么代价"。

## 原料：三条现成的来源

这份 playbook 不需要从零调研 —— 它建立在三批**已经完成**的产物上：

| 来源 | 提供什么 | 位置 |
| --- | --- | --- |
| **① KSPlayer 本体评估** | 它怎么做、**8 条可迁移的设计思想**、它的授权困境 | [`docs/01`](../docs/01-KSPlayer-设计思想与整体评估.md)（434 行） |
| **② 我们自己的决策记录** | 每个岔路口的选择与理由（定位 / 内核 / 产物 / 抽象 / 渲染 / 工程 / UI / 测试） | [`docs/02`](../docs/02-自建播放器决策记录.md)（413 行） |
| **③ 我们走完这条路的实测记录** | 每个阶段的判定门与证据；背后的原理 | `docs/03`–`docs/20` · [`knowledge/`](../knowledge/README.md) |

### 核心洞察

**`playerlearning`（本项目）本身就是一个"类 KSPlayer 项目"的活样本** ——
它从 Phase 0 走到 Phase 7，每一步都留下了票面、判定门、以及**踩过的坑**。
所以这份 playbook 要做的是**提炼**：把"我们花时间才搞清的"变成"你要走的路"。

## 与另外两个目录的分工

| 目录 | 回答的问题 |
| --- | --- |
| `docs/` | 我们**做过什么**（阶段交付物 + 可核对证据） |

## 一句话总纲

> **先定"内核与产物"，再立"边界"，最后才是 UI。**
>
> 顺序反了（先做 UI）会得到一个"看起来能跑、但每一层都改不动"的项目 ——
> 这正是 [`docs/01`](../docs/01-KSPlayer-设计思想与整体评估.md) §三 里，KSPlayer 用 8 条设计思想在防的事。
