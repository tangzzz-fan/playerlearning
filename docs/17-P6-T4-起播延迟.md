| 1 | **起播的 2 秒里，产品只占 ~0.4 秒**（修复前 ~1.2 秒），其余**由源决定** —— 旧基线把它记成"mpv 初始化 + MoltenVK + libplacebo 管线编译"是**错的**：那三项实测合计 **2–7 ms** |

## 二、指标 A 的口径要修 —— 先列先例，再改

`docs/15` 把指标 A 写成「`load` → 第一个 `state=playing`」，同一份文档里又写明它的**意图**：

| 先例原文 | 位置 |
| --- | --- |
| 「**A 起播延迟** … 用户点开之后**等多久出画**」 | `docs/15` **L19** |
| 「起播 1.5 s 是"**点开就出画**"的体感边界（> 2 s 会被读作"卡了"）」 | `docs/15` **L32** |

**实测结果：这两件事不是一个时刻，差了 1–3 个数量级。**

```
（真机 · 第一次冷启 · HTTP mp4）
... loadfile-sent=2.1  playing=2.0   file-loaded=57.5   vo-configured=256.4
                       ↑ 内核说"在播"     ↑ 文件才打开        ↑ 出画
```

`.playing` 落在 **2 ms**，比文件打开（57.5 ms）还早 —— 它根本不是在说"出画了"。
两条修正：

1. **终点改成出画**（`vo-configured`，mpv 的"视频输出已配置"）。这与 `docs/15` 写下的**意图**一致，
   只是把定义改成了能表达那个意图的那一个节点。
2. **测量方式改成内核打点**（毫秒、单调时钟），不再用每秒一行的 `[status]` 反推 ——
   `docs/15` 的基线正是后者，**分辨率 ±1 秒**。

> ⚠️ 注意这不是"把门槛调松"。`docs/15` 的 1500 / 2500 ms 两个值**没动**，
> 改的是"拿什么去比"。旧基线 2063 ms 与新的 178–234 ms **不可直接相减** —— 它们量的是两件事。

## 三、方法：内核时间线（分段才能归因）

`MPVKernel` 增一条时间线（`StartupTimeline`），用**同一台单调时钟**（`ContinuousClock`）在节点上打点：

| 节点 | 打在哪 | 为什么要在那里 |
| --- | --- | --- |
| `load-entered` | `load()` 入口 | 计时起点。`prepare()` 里的建句柄也是起播成本，不能被排除在外 |
| `handle-created` / `options-applied` / `initialized` | `mpv_create` / 设选项 / `mpv_initialize` 之后 | 把"初始化"这一段单独量出来（旧记载说它是 2 秒的主因） |
| `loadfile-sent` | `loadfile` 命令发出后 | 与下一节点相减 = **打开 + 探测** |
| `file-loaded` | `MPV_EVENT_FILE_LOADED` | mpv 说"这个文件我打开了" |
| `vo-configured` | 新观察的属性（首次变真） | **出画**（本票新加的节点，见 §二） |
| `playing` | 首次上报 `.playing`（在 `emit()` 里一处覆盖所有路径） | 保留它，正是为了看见它与出画的差距 |

设计上的三个决定：

- **每次 `load` 重置**（「停止 → 播放」的重新加载也算一次起播）——
  不重置的话读到的数字是上一轮的，**而且它们依旧自洽**（顺序对、单调、节点齐全），
  读的人看不出区别。已写成用例 `testStartupTimelineRestartsOnEveryLoad`。
- **不上 `PlayerKernelProtocol`**：假内核的耗时是假的，量它没有意义；而需要它的地方
  （Demo 的装配点）本来就握着具体内核类型。
- **取值全去重**（同名只记第一次）：起播关心"第一次到达"，不是"被改了几次"。

取证入口（Demo，**常开**，一行、零日志量）：

```
[startup] 出画=256ms · 内核说在播=2ms · 分段: load-entered=0.0 handle-created=0.8 … vo-configured=256.4
```

⚠️ **必须冷启一次 app 量一次**：内核句柄是懒建的（首次 `load` 才建），
同一实例里第二次 `load` 走的是"换文件"，与冷启不可比。
⚠️ 但它**不打开 mpv 的 verbose 日志** —— 那是 `-traceUpdates` 的做法，
而 mpv 的日志量会把 `devicectl --console` 在第 2 秒打爆（`P-058`），
**取证工具先于被测对象挂掉**。这里走的是事件回调 + 一次性读取，输出量恒定。

## 四、归因：把起播切成三段

### 4.1 三段各自的量值（修复前）

| 段 | 谁决定 | 实测 | 占比（实时源） |
| --- | --- | --- | --- |
| 建句柄 + `mpv_initialize`（含 MoltenVK / VkDevice / 管线） | 产品，基本固定 | **1.8 – 7.4 ms** | ≪1% |
| `loadfile` → `FILE_LOADED`（打开 + **流信息探测窗口**） | 产品配置 × **源怎么投递数据** | 拉取式 **57.5 – 80.9 ms**；实时 **1131 – 1206 ms** | ~35% |
| `FILE_LOADED` → `vo-configured`（解出第一帧） | **源的（下一个）关键帧间隔** | 86 – 4684 ms | ~65% |

**⇒ 旧记载「主导成本是 mpv 初始化 + MoltenVK/VkDevice + libplacebo 管线编译」被实测否定：
那三项合计 2–7 ms。**（`docs/16` §五 已加标注更正，原文保留。）

### 4.2 第二段的决定性对照（`file-loaded` 为什么是 1.15 秒）

关键差异不在播放器，在**源怎么投递**：

- **拉取式**（HTTP mp4 / HLS）：数据按网络速度**一次到手** ⇒ 探测窗口几乎不花时间（57–81 ms）。
- **实时投递**（RTSP 推流，`-re` 按 1× 送）：lavf 要"**读够一段媒体**"才能返回流信息，
  而 1× 投递下"一段媒体"= **一段真实时间** ⇒ **窗口直接变成用户等待**。

于是它是可消除的 —— 缩小窗口即可：

| 配置 | `file-loaded`（RTSP，同一条流） |
| --- | --- |
| 默认 | **1131 / 1237 / 1144 ms** |
| `demuxer-lavf-analyzeduration=0.2` | **380 / 336 ms** |

> 为什么旧基线没发现：它的源是 RTSP，而 `docs/15/16` 全都在量**落后量**，
> 没有把起播拆段 —— 1.15 秒和"缓存/GPU"混在一起，看起来像"产品初始化慢"。

### 4.3 第三段的决定性对照（出画为什么有时要 5 秒）

**同一个播放器、同一个服务器，只把源的 GOP 从 1.54–10.42 s 改成 0.5 s：**

| 源 | `loadfile`→`file-loaded` | **`file-loaded`→出画** | 出画 |
| --- | --- | --- | --- |
| `-c copy`（GOP 1.54 – 10.42 s） | 1206 / 1144 / 1147 ms | **698 / 4684 / 1082 ms** | 1905 / 5828 / 2230 ms |
| 重编码（`-g 12` ⇒ 0.5 s） | 1131 / 1237 / 1144 ms | **223 / 86 / 119 ms** | 1354 / 1322 / 1263 ms |

**第一段纹丝不动，第二段塌掉一个数量级** ⇒ 那一段归因给**源的关键帧间隔**，
不是播放器。（源素材的 GOP 实测 1.54 / 4.58 / 10.42 / 1.54 / 4.75 / 10.42 / 4.92 s —— 不规则，
是编码器按场景切换定的关键帧，所以等待时间方差极大：0.7–7.0 s 都在同一组里出现。）

**这一条与 `P6-T3` 里那 4.4 s 是同一族**：`P-052` ——
**不把验证环境的固有属性当产品缺陷去调参**。真实相机的 GOP 通常 1–2 s，
按 4.3 的数据，对应的出画应在 ~0.4–1.0 s（已落在目标内）。

## 五、改动（两处，都在产品里）

### 5.1 实时源的探测窗口：`StreamProbePlan`（新）

```swift
// 只在"窗口会变成用户等待"的那一类源上缩短它
if let analyzeduration = StreamProbePlan(resource.url).analyzeduration {
    setOption(handle, "demuxer-lavf-analyzeduration", String(analyzeduration))
}
```

| 源类型 | 窗口 | 依据 |
| --- | --- | --- |
| 实时投递（`rtsp` / `rtsps` / `rtmp` / `rtmps` / `rtmpe` / `rtmpt` / `rtmpts` / `srt` / `udp` / `rtp`） | **0.2 s** | 这一段的窗口**就是**用户等待（4.2 的对照） |
| 按需拉取（`http` / `https` / `file`） | **不动**（`nil`） | 那里窗口不构成等待（57–81 ms），而它存在的意义是让 lavf 看清流信息 —— **拿没量到的好处换没量到的风险**，不做 |

⚠️ scheme **归一化大小写**：`URL` 会原样保留（`RTSP://` 的 scheme 是 `"RTSP"`），
不归一化这条规则会**静默失效**（症状只是"起播慢一秒"，谁也不会来这里查）。

### 5.2 内核状态说谎：`pause` 只在"有东西能让它描述"时才解读

**症状**（起播埋点照出来的）：`load()` + `play()` 之后 **2 ms** 内核就报 `.playing`；
对**打不开的文件**更荒谬 —— 先报 `.playing`、再报 `.failed`（实测里 `.playing` 会把 `.failed` **盖掉**）。

**根因**：`pause` 是个**全局属性**，mpv 会在与播放无关的时机把它重置回 `no`：

| 时刻 | 内核状态 | `pause` | 旧判据（播放列表非空）看到什么 |
| --- | --- | --- | --- |
| 刚发完 `loadfile`，文件还没打开 | `.preparing` | `no` | 列表里**已有**那个条目 ⇒ "非空" ⇒ 报 `.playing` |
| 文件打不开，已经失败 | `.failed` | `no` | 失败条目**还在**列表里 ⇒ 报 `.playing` **盖掉 `.failed`** |

**修法**：加一条**纯逻辑规则**（`PlayerState.pauseDescribesPlayback`），
两道判据都过才解读 `pause`：

| 状态 | 能不能解读 | 为什么 |
| --- | --- | --- |
| `.readyToPlay` / `.playing` / `.paused` | ✅ | 有打开的文件，`pause` 描述的就是它 |
| `.idle` / `.preparing` / `.finished` / `.failed` | ❌ | 没有"正在播的东西"可以让它描述 |

> 为什么不是靠"下游正好挡住"：装配层 `PlayerStateMachine` 确实把 `.preparing → .playing`
> 列为**非法边**，所以界面从来没显示错状态 —— 但**内核自己的 `state` 与 `snapshot()`
> 一直在给假答案**，任何别的消费者都会拿到同一句假话。判据同 `P-038`。

## 八、没做的项（**没测就不改**）

| 项 | 为什么没动 |
| --- | --- |
| 给实时源**再调小**窗口（0.2 → 0.1） | 没测过收益；且窗口越短，lavf 看清流信息的余量越小 —— 要拿真实相机复测才敢动 |
| 拉取式源也缩短窗口 | 实测那里本来只有 57–81 ms（`docs/16` §五 的假设已否）；缩短它是**净风险** |
| 关键帧等待的"优化"（如让服务器/相机发一个 IDR） | 那是**源的属性**：`P-052` 的纪律 —— 不把验证环境的固有属性当产品缺陷去调参 |
| 起播期间再多打几个节点（解码器初始化、音频链路） | 现有分段已能解释 99% 的墙钟；**再多分段只是让表更长** |
| HLS 直播（`#EXT-X-PLAYLIST-TYPE:EVENT`）的起播 | 本轮 HLS 只测了 VOD ladder。**未测**既有 HLS 直播源，也没有可控环境 |

## 九、结论一句话

**起播的 2 秒里产品只占 ~0.4 秒（修复前 ~1.2 秒、更早的记载把它记成了"GPU 初始化"）；
产品那一项靠"实时源缩短流信息探测窗口"砍掉 65%，剩下的由源的关键帧间隔决定 ——
而顺手照出来的第二个缺陷（内核在文件还没打开时就报"在播"，并把 `.failed` 盖掉）
也一并修掉，它正是那条被记成"偶发资源争抢"的用例的真正成因。**
