## 二、先证明"真机能连上"（否则后面全是空中楼阁）

### 2.1 一个 6 毫秒的失败

```
[mpv/ffmpeg] tcp: Connection to tcp://192.168.2.217:8765 failed: No route to host
```

看起来像网络不通。但同一时刻：宿主防火墙**关**、服务在 `*:8765` 上 `LISTEN`、
宿主自己 `curl` 拿到 `206`。**而且它 6 毫秒就返回了** —— 包根本没发出去。

真因：iOS 14+ 需要 `NSLocalNetworkUsageDescription` 才有"访问本地网络"的授权入口。
补上之后，同一条 URL **立刻通了**。完整判据见 **`P-056`**。

### 2.2 通了之后的数字

| 量 | 值 |
| --- | --- |
| `preparing → readyToPlay` | **96 ms** |
| `readyToPlay → playing` | **3 ms** |
| 画面 / 音频 | 1280×720 · 48000 Hz 立体声（`audio-out` 已建立） |

### 2.3 服务端看到的三个 Range 请求 —— **正面印证 `P-052`**

```
[header] Range: bytes=0-            ← 从头读
[header] Range: bytes=48-           ← 试探
[header] Range: bytes=7568797-      ← 读**文件尾**
```

第三个是去读 **`moov`（mp4 的索引，常在文件尾部）**。
这解释了 `P-052` 为什么成立：**播放 mp4 必须能回退读**，
而 `python -m http.server` 不支持 Range ⇒ 线性流 ⇒ 一个包都读不到就 "EOF"。
⇒ 本项目的验证**一律用 `Tools/serve-range.py`**，不用 `http.server`。

## 三、`G5` 判定：可控弱网（限速 **45 000 B/s** ≈ 0.36 Mbit/s）

720p 实时播放需要约 **146 KB/s**（7.6 MB / 52 s）。限到 45 KB/s ⇒
**供给只有需求的 1/3**，缓存必然反复耗尽 —— 这正是"弱网"该有的样子，而且是**可控、可复现**的。

### 3.1 三项判定

| 判定项 | 结果 | 证据（`[status]` 每秒一行，共 107 行） |
| --- | --- | --- |
| 弱网下**不崩** | ✅ | 107 秒内 `state` **始终 `.playing`**，从未出现 `.failed`；进程全程存活 |
| 有**缓冲提示** | ✅ | `buffering` 反复 `true ↔ false`（UI 上就是状态行末尾的「· 缓冲中」）；全程多数时间 `true` |
| **恢复后自动继续** | ✅ | 位置反复"停住 → 自行推进"，**无需任何用户操作**（见下表） |

### 3.2 位置轨迹（节选，每 8 条取 1 条）

```
[status]   8.218 state=playing t= 0.00/52.21 progress=0.000 buffering=true    ← 起播等缓存
[status]  16.439 state=playing t= 4.00/52.21 progress=0.077 buffering=true
[status]  24.732 state=playing t= 4.00/52.21 progress=0.077 buffering=true    ← 停住（缓存耗尽）
[status]  33.071 state=playing t= 8.00/52.21 progress=0.153 buffering=true    ← 自行恢复
[status]  49.651 state=playing t=12.00/52.21 progress=0.230 buffering=true    ← 又停
[status]  57.921 state=playing t=16.50/52.21 progress=0.316 buffering=true    ← 又恢复
[status]  74.420 state=playing t=20.75/52.21 progress=0.397 buffering=false   ← 缓冲**结束**
[status]  99.101 state=playing t=24.50/52.21 progress=0.469 buffering=false
[status] 107.281 state=playing t=25.75/52.21 progress=0.493 buffering=true
```

**吞吐核对**：107 秒播到 25.75 秒 ⇒ 实际约 **35 KB/s**（限速 45 KB/s − 协议/Range 开销）。
与"实时需要 146 KB/s"的差距，正是反复停顿的原因 —— **不是产品在抖，是网确实弱**。

## 四、`P5-T4`：请求头的证据在**服务端**，不在我们的代码里

真机侧自己声明的（`-headers "X-Player-Learning: …,Referer: …"`）：

```
[direct] headers=Referer: http://example.com/watch,X-Player-Learning: p5t4-real-device
```

**服务端收到的原文**：

```
[header] User-Agent: PlayerStack/1.0
[header] Referer: http://example.com/watch
[header] X-Player-Learning: p5t4-real-device
[header] Icy-MetaData: 1                 ← ffmpeg 默认
```

⇒ **全局 UA 与 per-file 自定义头都真的到了服务端**（不是"我调过 setOption"）。
`--echo-headers` 这个开关就是为此存在的 —— 判据沿用项目一贯那条（同 `P-050`：设了 ≠ 它认了）。
