# 33 · 处理器链（M2 第一步）

> 一句话：**帧到手之后、上屏之前，插一条可以有多节、每节都可能"慢半拍"的加工链，
> 而播放不能被任何一节拖住。**

代码：`Sources/PlayerCore/FrameProcessor.swift` · 测试 `Tests/PlayerCoreTests/FrameProcessorTests.swift`（16 条）
· 适配器接缝 `MPV/Sources/PlayerMPV/MPVRenderOutput.swift`（`framePipeline` / `processed(_:target:)`）

---

## 一、为什么要单独一层（ELI5）

想象流水线上有一箱箱货（帧）每秒 60 箱送过来，末端是显示屏。

- **叠加层**（字幕）像在箱子上**贴一张标签**：箱子还是那箱货，贴完就往下走。
  标签画得慢一点没关系，最多这张没贴上，下一张再贴。
- **加工层**（LUT / 深度 / 打码）像把货**换掉**：下游拿到的是另一箱。
  换货要时间，而且换得慢就会**堵住整条线**。

今天项目里只有第一种（`subtitleSource`），第二种是这一层要解决的。
两者混在同一个 `step()` 里会让"哪个是装饰、哪个是内容"永久分不清 —— 所以先分家。

**"慢半拍"是这个方案的核心**：换货员来不及换，就**先把上一箱换好的递过去**，
同时告诉末端"这是上一箱的，晚了 2 帧"。这比"停下来等"和"扔一箱"都好：
前者肉眼可见地卡，后者连画面都少了。

## 二、三个类型与它们的契约

```swift
public protocol FrameProcessor<Frame> {
    associatedtype Frame                      // 适配器里是 MTLTexture
    var identifier: String { get }             // 稳定标识（顺序 + 旧结果归属）
    var order: Int { get }                     // 越小越先跑
    func process(_ frame: Frame, context: FrameContext) -> FrameProcessorOutput<Frame>
}

public enum FrameProcessorOutput<Frame> {
    case unchanged      // 没动手
    case replaced(Frame) // 处理完了，用这个
    case notReady        // 异步还没好 —— 怎么顶由策略决定，不由处理器决定
}
```

| 契约 | 为什么这样定 |
| --- | --- |
| 结果只有三种 | 加第四种（"丢弃这一帧"）就等于允许实现方**自己决定卡顿**，而调用方看不出原因 |
| `notReady` 不携带"我上次那张" | 谁记得旧结果、记多久，是**调度**的事。让处理器自己管，每个实现都会各写一遍且写错 |
| `unchanged` ≠ `replaced(同一帧)` | 前者"没动手"，后者"处理过了"。混起来调用方会以为有加工发生，`applied` 就失去意义 |

## 三、顺序是语义，不是实现细节

`order` 决定执行次序。**同 `order` 时按 `identifier` 字典序**。

这不是洁癖：Swift 的 `sort` **不稳定**，两个同 `order` 的处理器不设次序，
同一份输入可能今天 a→b、明天 b→a —— 而"打码在字幕之下"这类需求正是靠顺序表达的，
顺序一漂，画面就时对时错，且**不可复现**。

还有一条容易忽略的后果：**下游会继承上游的旧结果**。
A 慢了、用旧结果顶替，B 收到的是 A 的旧帧（`testHoldIsPerProcessorNotGlobal` 就钉这一条）。
所以链越长，"迟到"会被逐节叠加 —— 这也是 `maxLagFrames` 存在的理由。

## 四、迟到策略：两档，没有第三档

| 策略 | 行为 | 用在 |
| --- | --- | --- |
| `.passthrough` | 原帧直接过 | 结果必须与当前帧严格对应，宁可不加工 |
| `.holdLastResult(maxAgeFrames:)` | 用该处理器**上一次**的结果；超过 `maxAgeFrames` 帧退回 passthrough | 深度 / 推理这类"画面内容变化慢"的处理器 |

**为什么有上限**：迟到 5 帧的结果对应的是**另一幅画面**，叠上去就是错位（2D→3D 会晕）。
上限是**语义**，不是性能参数 —— 「宁可这一帧不加工」比「加工错」好。

**边界有三条，都钉了测试**：

- `age == maxAgeFrames` 仍然复用（`testHoldReusesAtExactlyMaxAge`）
- `age > maxAgeFrames` 放弃（`testHoldGivesUpBeyondMaxAgeAndFallsBackToTheRawFrame`）
- `age < 1`（时钟倒退 / reset 前的残留）**一律不复用**（`testResultFromTheFutureIsNeverReused`）

默认 `maxAgeFrames: 2`。这个数**没有实测依据**，是"60 fps 下 33 ms 以内"的量级猜测，
等第一个真处理器接上再量（见 §六）。

## 五、插入点：只能在这里

```
makeTexture(from: buffer)  →  帧已经在 GPU 上（零拷贝）
        ↓
processed(texture, target: target)   ← 唯一插入点（本层）
        ↓
draw(texture:drawable:content:)      →  上屏
```

三个位置都试过的结论：

| 想放的位置 | 为什么不行 |
| --- | --- |
| `makeTexture` 之前（CPU 侧 `CVPixelBuffer`） | 那时还没有 GPU 纹理；在 CPU 上改 4K 一帧就是几毫秒起 |
| 放进 `draw` | 那里已经在填着色器参数，等于**每种处理器都要改一遍 `draw`** —— 又把平台做成定制 |
| 另开一个 pass 之后 | 那是处理器自己的事（它可以在内部开 pass），不该由管道的调用点承担 |

`framePipeline` 默认 `nil` ⇒ 这段代码**根本不执行**：不建上下文、不分配、不碰纹理，
与没有这一层时的渲染逐字节一致。

### 必须记得的一步

```swift
output.resetFramePipeline()   // seek 之后必调
```

不调的话，跳转后的第一帧会被跳转前的旧结果顶替 —— 画面**停在旧位置**，
直到处理器重新就绪。`attachIfNeeded()` 里已自动调（换片源等于换语义）。

## 六、怎么加第一个处理器（下一个动作）

> ✅ **已落地**：[`docs/34`](34-首个处理器-LUT.md) 按下面四条做了 `LUTFrameProcessor`
> （GPU pass + 3D 纹理 + 像素级对账 + 5 个变异体）。下面这段保留为"加下一个处理器"的清单。

1. 实现 `FrameProcessor`，`Frame = MTLTexture`，`identifier` 用**语义名**（`"lut"` / `"depth"`），
   不要用类型名 —— 换算法不换名字会让旧结果被误认成新算法的结果。
2. `order` 想清楚谁在谁下面。
3. 异步的处理器：在内部队列算，`process` 只做两件事 —— 投递本帧、返回上一次算好的（或 `.notReady`）。
   **不要在 `process` 里等**，那是把"慢"变成"卡"的唯一方式。
4. 接上之后必须量的两件事：
   - **单帧预算**：`docs/25` 的真机 4K **按源码 44.34 ms**（21.8 fps）才是含处理器的预算，
     不是按上屏的 11.51 ms（`docs/32` §5.3）
   - **`maxLagFrames` 的合理值**：靠 `lastPipelineOutput.applied` 的实测分布定，不要沿用默认的 2

## 七、已验证 / 未验证

**已验证**（本机当场跑）

| 项 | 结果 |
| --- | --- |
| `FrameProcessorTests` | 16 条全绿 |
| 变异验证 | 5 个变异体 **全部被抓住**（上限差一帧 / 去掉时钟倒退保护 / 顺序反向 / 不记迟到帧数 / 换处理器不清旧结果） |
| 一条过程事故 | 第一版的 5 条测试是**假绿**（分支没进入），补正断言后才暴露 ⇒ [`P-097`](PITFALLS.md) |
| 既有套件 | 304 + 98 + 0 = **402 条全绿**（原 386，+16） |
| iOS 构建 | `xcodebuild -scheme PlayerMPV -destination 'generic/platform=iOS'` → `BUILD SUCCEEDED` |

**未验证**（别当成结论）

- **一个真实处理器都还没有**。现在能证明的是"顺序与迟到策略按契约工作"，
  **不能**证明"插上处理器之后还能实时"。
- **`MTLTexture` 版本的整条链没跑过**：`Frame = MTLTexture` 是编译期成立的，
  但"处理器返回另一张纹理、`draw` 用它上屏"这一段没有实机画面取证。
- 迟到分布的实测数据一条都没有，`maxAgeFrames: 2` 是猜的。
