# 15 · `P6-T2` 直播延迟：**指标口径 + 测量方法 + 基线**

> **日期**：2026-10-16 · **环境**：iPhone 16 Pro（真机）· `mediamtx v1.21.2` · `ffmpeg 9.0.2`
> **票面**（`docs/03` 三 · `P6-T2`）：延迟测量与调优（给出**可量化**的延迟指标）
> **进入条件**：`P6-T0` 调研完成（✅ `docs/13`）· `G5` 通过（✅ 2026-10-16）
>
> ⚠️ 本票卡在一个**必须先答的口径**上：`docs/13` §五 说得很清楚 ——
> **「延迟」必须写清是端到端还是播放器内部，否则数字之间不可比**，
> 且把三条候选标成「**先登记不结论**」。本报告就是那个结论。

## 一、结论（先说）

**定两个指标，都自动可采、都落在同一根时间轴上：**

| # | 指标 | 定义 | 单位 | 量什么 |
| --- | --- | --- | --- | --- |
| **A** | **起播延迟** | `load` → 第一个 `state=playing` 的墙钟差 | ms | 用户点开之后**等多久出画** |
| **B** | **直播落后量** | **推流端已推到的媒体时间** − **播放端 `time-pos`** | ms | 画面比"源"**落后多少** |

**门槛值**（先给数，再给依据 —— 依据是**产品判断**，不是行业标准）：

| 指标 | 目标 | 可接受 | 现状（默认参数） |
| --- | --- | --- | --- |
| A 起播延迟 | **≤ 1500 ms** | ≤ 2500 ms | **2063 ms** ⇒ 未达标 |
| B 直播落后量 | **≤ 1000 ms** | ≤ 3000 ms | **≈ 9000 ms** ⇒ **远未达标** |
| B 的稳定性 | 波动 ≤ ±500 ms | — | **±50 ms**（极稳，见 §四） |

> **目标值的依据**：① 互动类直播（连麦 / 竞猜 / 弹幕对时）要 < 1 s 才有"对话感"；
> ② 3 s 是大部分人开始明显感到"这不是直播"的量级（HLS 常规是 6–30 s，WebRTC 是 < 0.5 s）；
> ③ 起播 1.5 s 是"点开就出画"的体感边界（> 2 s 会被读作"卡了"）。
> ⚠️ **这三条是产品判断**，写在这里是为了**将来有人不同意时知道在跟什么比**，不是引用某个标准。

---

## 二、为什么定这两个（而不是 `docs/13` 里那三条候选）

`docs/13` §五 登记的三条：①**烧时间码 + 像素比对** ②秒表对照 ③读 mpv 的 `demuxer-cache-time`。
逐条判：

| 候选 | 判 | 理由 |
| --- | --- | --- |
| ① 烧时间码 + 截图比对 | ❌ **不作为主指标** | 它量的是「**屏幕像素**上的墙钟 − 真实墙钟」。而我们真正关心的是"画面落后源多少" —— 这两者只差**编码+合成**那一小段（1–2 帧），却把误差源从"一条时间轴"变成"两条 + 图像识别"。**收益小、误差大**。留作将来要"眼见的延迟"时的补充（触发条件：需要对外承诺"屏幕延迟"数字） |
| ② 秒表对照（同框录屏数帧） | ❌ | 不是自动化，且要人工读帧 —— 与本项目"能自动就别手动"的方向相反 |
| ③ 读 `demuxer-cache-time` | ❌ **不够** | 那只是**缓冲区余量**（播放位置之后还有多少数据），**完全不含"源推了多久"** —— 它是"播放器内部"的量，无法回答"我比源落后多少" |

**指标 B 与③的区别就在一句话：把"源那一端"也拉进来。**
`推流端已到哪` 与 `播放端在哪` 一减，才是用户感受到的那个落后量。
而两端**跑在同一台机器、同一个墙钟**上（见 §三），所以对齐误差 ≪ 1 帧。

## 三、怎么测（**方法**，可复现；harness 是一次性的，不留仓库）

### 3.1 两侧各出什么

```bash
# 源：RTSP 服务器（配置见 /tmp/mediamtx.yml；⚠️ 空配置不行，见 P-060）
mediamtx /tmp/mediamtx.yml

# 推流端：-re 实时、单次不 loop（loop 会让媒体时间回绕，指标就失效了）
ffmpeg -re -i <素材> -c copy -f rtsp -rtsp_transport tcp \
  rtsp://127.0.0.1:8554/live -progress pipe:1 -nostats
#   ⇒ out_time=HH:MM:SS.ffffff  ← 「已推到的媒体时间」（权威值）

# 播放端：真机直连（-directURL 把 URL 原样交给内核，不下载）
xcrun devicectl device process launch --device <UDID> --console \
  --terminate-existing com.playerstack.demo -- -directURL rtsp://<MACIP>:8554/live
#   ⇒ 每秒一行 [status] … t=…/…  ← 「正在显示的媒体时间」
```

### 3.2 ⚠️ 关键一步：**把两路合到同一时基**

`out_time` 是**媒体时间**，`[status]` 里的时间戳是 **App 自己的 origin** ——
两者**不同基**，直接相减得到的是垃圾（这是这一票最容易做错的地方）。
做法：用**一个采集进程**同时拉起两个子进程，给**每一行**盖上同一个 `time.time()` 起点。

### 3.3 算法

```
lag(t) = pushed_media(t) − time_pos(t)          ← 指标 B
  · pushed_media(t)：`out_time` 每 ~0.5 s 一行 ⇒ 相邻两行之间**线性插值**
  · time_pos(t)：播放端每秒一行的 `t=`
起播延迟 = (首个 `state=playing` 的墙钟) − (`[direct] url=…` 那一行的墙钟)   ← 指标 A
```

### 3.4 一条**前提必须被验证**（否则指标 B 塌掉）

指标 B 假设「`-re` 是真 1× 推流」。本次实测推流端媒体时间推进速率 = **1.003×** ✔
（见 §四）。**若不验这一条，落后量里就混进了推流端的偏差，而它看起来完全正常。**

## 四、基线（**默认参数**下的现状）

真机 iPhone 16 Pro · 55 秒采集 · 素材 52 s · `preparing → playing` 起播阶段 3 拍缓冲

| 项 | 值 |
| --- | --- |
| **A 起播延迟** | **2063 ms**（`[direct]` → 首个 `playing`） |
| 起播阶段 `buffering=true` | 3 拍（约 2 秒） |
| 推流端推进速率 | **1.003×**（前提成立 ✅） |
| **B 稳态落后量** | **8970 – 9064 ms**（38 拍样本，**均值 ≈ 9008 ms**） |
| 全程 `state` | 始终 `playing`，**0 次 `failed`** |

**原始片段**（同一时基，`墙钟 / 播放位置 / 已推媒体 / 落后量`）：

```
 8.805   0.00    9.25   9245 ms   ← 刚进入 playing
12.994   4.46   13.44   8983 ms   ← 起播缓冲结束
17.125   8.55   17.56   9008 ms   ← 之后逐秒几乎不动
30.361  21.84   30.81   8970 ms
47.587  39.00   48.02   9024 ms
```

### 4.1 这个"恒定"本身就是判据

落后量**不随时间增长**（38 拍内 ±50 ms）⇒ 它是**缓冲深度**，不是"解码追不上源"的漂移。

**两者的处置完全相反**：
- **漂移**（越拉越远）⇒ 是性能/带宽问题，改缓冲参数没用；
- **恒定深度** ⇒ 是**缓存配置**决定的，**可调**。

⇒ 于是直接去看配置：`applyNetworkOptions` 里设了 `cache=yes`，
**但没设 `cache-secs`** —— 而 mpv 对流的 `cache-secs` 默认是 **10 秒**。
**9 秒落后量 = 10 秒缓存深度的必然结果，因果闭合。** 这就是 `P6-T3` 的抓手。

## 五、本票不做什么

- **不调参**（那是 `P6-T3`）：本票只把"量什么、怎么量、现在多少"钉死。
- **不新增仓库脚本**：采集与分析是**一次性 harness**（方法见 §三）；
  按项目口径「知识留在 `docs/`，机器不留在 `Tools/`」。
- **不承诺"屏幕延迟"**：指标 B 不含"播放位置 → 像素"的最后一段（1–2 帧）。
  要对外承诺那个数字时，按 §二 候选 ① 补。

## 六、结论一句话

**延迟有了可复现的量化口径（起播 / 落后量，同一时基），基线是
「起播 2063 ms · 落后量 ≈ 9 s 且恒定」——`cache-secs` 默认 10 s 是那个 9 s 的来源，
调参留给 `P6-T3`。**
