# 32 · 帧管道路线：不走播放器那条路的规划

> 前提：董事长明确**不走 KSPlayer 路线**（不做"又一个能播一切的播放器库"）。
> 本文给出替代路线：**定位、场景、能力缺口、三阶段打法、边界**。
> 原则：只写从代码与实测里能站住的东西；没量过的标「未验证」。

---

## 一、结论

**别做播放器，做"视频帧的可编程中间件"。**

- 播放器路线的交付物是**一块能播的屏幕** —— 这块屏幕，KSPlayer / VLCKit / AVPlayer 已经交付得足够好
- 中间件路线的交付物是**每一帧的像素 + 一条能插处理器的管道** —— 这一块，Swift 生态里没有成熟方案
- 前者拼"格式覆盖"，是军备竞赛；后者拼"帧的出口"，是接口位置

一句话：**格式覆盖是地基，不是卖点。卖点是帧到哪里、能变成什么。**

---

## 二、为什么不走播放器路线（四条，不是偏好）

| # | 事实 | 后果 |
| --- | --- | --- |
| 1 | 播放器库的护城河是**格式覆盖**，而覆盖度取决于 FFmpeg/libmpv，人人可得 | 你花两年追上的，别人换个内核就追平 |
| 2 | `AVPlayer` 覆盖了 95% 的消费场景（mp4/HLS/DRM），剩下的 5% 长尾里还有 VLCKit 和 KSPlayer | 你的用户是"那 5% 里再挑剩下的"，绝对数很小 |
| 3 | 播放器库的 API 重心是**控制**（play / pause / seek / 音量 / 手势），做深了就是做 UI | 越做越像"帮别人写 App"，而不是做一个可复用的东西 |
| 4 | 我们已经有的**唯一稀缺资产**是 `render API` 的帧出口（真机 4K 11.51 ms） | 播放器路线用不上这份资产，等于把它废掉 |

第 4 条是最关键的：**手里有别人没有的东西，却去红海里比谁更便宜，是战略错误。**

---

## 三、新定位：帧可编程中间件

```
                 ┌──────────── 你的 App（业务）────────────┐
                 │  想对画面做什么，由你决定               │
                 └───────────────┬────────────────────────┘
                                 │ 帧（CVPixelBuffer / MTLTexture）
                 ┌───────────────▼────────────────────────┐
                 │  PlayerStack（中间件）                 │
                 │  解码 · 时序 · 处理器链 · 合成 · 上屏   │
                 └───────────────┬────────────────────────┘
                                 │
             屏幕 / 眼镜 / 模型 / 编码器（多个出口）
```

与"播放器库"的六条差别：

| 维度 | 播放器库 | PlayerStack（本路线） |
| --- | --- | --- |
| 交付物 | 一块能播的屏幕 | 每一帧 + 一条管道 |
| API 重心 | 播放控制 | **处理器注册 / 时序策略 / 合成** |
| 用户诉求 | "我要能放这个文件" | "我要在这一帧上做点什么" |
| 竞争状况 | 三方夹击，红海 | 只能自己啃 libmpv C API，蓝海 |
| 护城河 | 无 | 帧出口 + 时序统一 + 实测数据 |
| 失败形态 | 播不动 | 帧被卡住（可测、可归因） |

## 四、五类场景，按"现在能不能做"排

| 场景 | 需要什么能力 | 现状 | 缺什么 |
| --- | --- | --- | --- |
| **眼镜 2D→3D**（Jove） | 每帧估深度 → 双眼视口合成 → 外屏 | 帧已到手；Jove 侧已有 `MetalDepthCompositor` 与 `VideoDepthEngine`（AVAssetReader 版） | ① 把深度引擎接到实时帧上（现在是逐帧读文件）② 异步处理器的时序策略 |
| **AI 叠加** | 端侧模型跑在帧上，结果画回画面 | 帧已到手 | ① 处理器协议 ② `CVPixelBuffer` ↔ `MLMultiArray` 的转换样板 ③ 异步结果与帧对齐 |
| **专业监看** | LUT 调色、示波器、安全框、逐帧步进 | 帧已到手；逐帧能力有（`seek` + `pause`） | ① GPU 处理器（LUT 要 GPU）② 4K 性能（见 §五） |
| **无障碍 / 隐私** | 放大、高对比、色盲校正、本地人脸打码 | 帧已到手 | ① 处理器协议 ② 检测结果的坐标变换（视频坐标 → 视图坐标） |
| **直播与录制加工** | 多路合成、水印、边播边录 | 直播已验（RTSP / HLS 真机通）；帧已到手 | ① 多输入合成 ② 编码输出（`AVAssetWriter` 侧） |

**共同点**：全部只需要"能拿到帧 + 能改帧"。这正是我们已经有的那半段。

## 五、能力缺口（按重要性）

### 5.1 没有处理器协议 —— 现在"加工"是硬编码的

今天的自绘字幕是这样接进去的（`MPVRenderOutput`）：

```swift
public var subtitleSource: SubtitleOverlaySource?   // 只有一个，写死的类型
private var liveSubtitleText: String = ""
```

也就是说：**管道目前只有一种处理器，而且类型是固定的。** 要做第二条（LUT / 深度 / 打码），
只能再往 `MPVRenderOutput` 里加属性 —— 这是把平台做成一次性的定制。

必须抽出来：

```swift
public protocol FrameProcessor: AnyObject {
    var order: Int { get }
    func process(_ frame: inout VideoFrame, context: FrameContext) -> FrameProcessorResult
}
// FrameProcessorResult: .passthrough / .replaced(VideoFrame) / .dropLastResult(异步未就绪)
```

### 5.2 没有异步处理器策略 —— 而深度/AI 天生异步

渲染预算是 **11.51 ms/帧**（真机 4K，暂停压 120 帧测得）。深度估计与端侧推理都在**十几到几十毫秒**量级，
同步做必然掉帧。所以必须有"用上一帧的结果 / 直接透传 / 跳过"的显式策略，而不是让调用方自己撞。

这是**这条路线的核心技术难点**，也是最值钱的部分：**一个处理器慢了，不能让播放卡住。**

### 5.3 ⚠️ 4K 性能：一旦插入处理器，之前的"不上 GPU 桥"结论要重算

这是本轮最重要的发现，必须写清楚：

| 场景 | 实测数字 | 含义 |
| --- | --- | --- |
| 4K，**按上屏**（mpv 渲染完 + 只算上屏那一步） | **11.51 ms**（86 fps） | 看起来很美 |
| 4K，**按源码**（mpv 完整渲染一帧） | **44.34 ms**（21.8 fps） | 这才是处理器的预算 |

之前判"不上 GPU 桥"，比的是"仅 mpv 渲染 11.51"与"整帧 11.51"——两者只差 0.01–0.02 ms，
结论是"Metal 那段在真机上几乎免费"。

**但这个结论的前提是"我们除了上屏什么都不做"。** 一旦处理器链要跑 GPU（LUT / 深度 / 推理），
整条链就要重新算：mpv 用 `MPV_RENDER_API_TYPE_SW`（CPU 渲染）出 4K 本身已经 44 ms，
再叠加 GPU 处理器，4K 会明显低于实时。

⇒ **M2 必须重开"要不要 GPU 桥（`MPV_RENDER_API_TYPE_OPENGL`/Metal）"这个决策**，
判据不再是"上屏那段贵不贵"，而是"**加上处理器之后还能不能实时**"。

### 5.4 没有多处理器叠加与顺序

字幕在视频之上、打码在字幕之下、水印在最上面 —— 顺序是语义，不是实现细节。
现在一条都没有，所以还没暴露这个问题。

### 5.5 没有帧时间戳的对齐约定

字幕已经用 `time-pos` 查表（正确做法）。但异步处理器的结果是"晚到的"：
深度图对应的是 3 帧前的画面。**必须显式定义"结果与帧的对齐规则"**，否则 2D→3D 会晕。

## 六、三阶段打法

| 阶段 | 目标 | 交付物 | 验收判据 |
| --- | --- | --- | --- |
| **M1 帧在手**（已完成） | 帧能出来、能上屏、能测 | render API SW 输出 · 自绘字幕 · 三层取证 | 真机 4K 11.51 ms · 三张截图文本互不相同 |
| **M2 帧可编排** | 处理器能插、慢了不卡 | `FrameProcessor` 协议 · 同步/异步策略 · 3 个参考实现（字幕 / LUT / 深度）· **GPU 桥决策重开** | ① 接 3 个处理器不掉帧 ② 故意让一个处理器慢 3 倍，播放不卡 ③ 4K 下仍 ≥ 30 fps |
| **M3 帧可变现** | Jove 端到端 + 对外可用 | Jove 在线浏览（直链/HLS）+ 2D→3D 全链 · 文档 · 示例 | 眼镜上连续 10 分钟不崩、不晕、帧率达标 |

**顺序不能换**：M2 的协议要是先给 Jove 写死了，M3 就得推倒重来。

> **M2 进度（2026-10-18）**：协议 + 迟到策略已落地（[`docs/33`](33-处理器链.md)），
> 第一个真实处理器 LUT 已落地并做了像素级对账（[`docs/34`](34-首个处理器-LUT.md)）。
> 三个验收判据里 **③ 4K 帧率仍无数字**，**② "故意慢 3 倍不卡"也还没做**（没有异步处理器）。

## 七、商业形态：卖什么

| 层 | 形态 | 收不收钱 |
| --- | --- | --- |
| 库 | MIT 开源（`PlayerCore` / `PlayerUI` / `PlayerMPV`） | 不收 —— 它是获客与信誉 |
| 处理器集 | 深度 / LUT / 打码等参考实现 | 基础免费；高级（如高质量深度）可考虑 |
| 企业 | 定制处理器 · 优先支持 · 合规包（`compliance/`） | 收 |
| 产品 | **Jove 眼镜**（真正的终端产品） | 这才是主营业务 |

判断依据：**播放器库本身很难直接卖钱，但"能拿到帧"这件事能让产品做得出来。**
所以开源库的价值不在授权费，在**降低自己做产品的成本 + 建立技术信誉**。

---

## 八、不做什么（边界，写死）

| 不做 | 理由 |
| --- | --- |
| 成品播放器 UI（播放列表、手势全家桶、皮肤） | 那是 App 的事，做进去就把库变成产品 |
| 以"格式数量"当卖点 | 内力在 FFmpeg，不在我们 |
| DRM / FairPlay | 与 libmpv 的模型不兼容，是另一条产品线 |
| Android / 桌面端 | 没有第二个消费者之前不做，`P-083`：别把"我们暂时不需要"写成"它不适合" |

## 九、未验证（别拿它当结论）

| 问题 | 状态 |
| --- | --- |
| 4K + 一个 GPU 处理器链路的实际帧率 | **未验证** —— 只有 mpv 单独的数字（44.34 ms 按源码） |
| 深度估计在 A17 Pro 上的单帧耗时 | **未验证** —— Jove 侧现有引擎是离线逐帧读文件，不是实时链路 |
| 异步处理器的"用旧结果"策略在视觉上是否可接受 | **未验证** —— 需要人眼判断（2D→3D 尤其敏感） |
| GPU 桥（Metal/OpenGL 后端）在真机上的可用性 | **未验证** —— `MPV_RENDER_API_TYPE_SW` 已验，GLES 未验 |
