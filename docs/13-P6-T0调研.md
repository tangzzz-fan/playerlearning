# 13 · `P6-T0` 直播技术调研（`Phase 6` 的进入条件）

> **日期**：2026-10-15 · **环境**：macOS 27 / Xcode 27.0 · 真机 iPhone 16 Pro
> **调研问题**（`docs/03` §三 `P6-T0` 原文）：libmpv 对 RTSP/RTMP 的支持现状 ·
> 低延迟参数（`cache-secs=0` / `--untimed` / `demuxer-lavf-*`）· 追帧策略
> **进入条件**：`Phase 5` 的 `G5` 通过，**且本调研给出明确结论**。在此之前 `Phase 6` 不排期。

---

## 结论（先说）

| 问题 | 结论 | 证据强度 |
| --- | --- | --- |
| **自建 LGPL 产物认不认 RTSP/RTMP** | ✅ **认**（且**不需要重新构建**） | **强**：产物字符串 + **运行时探针走到 socket 层** |
| **有没有参考实现可抄** | ❌ **没有** | 强：`vendor/ksplayer` 里直播只有**一行选项声明**，零实现 |
| **低延迟参数在不在** | ✅ 11 个候选选项名都在产物里 | 中：**"名字在"≠"生效"**，必须实测（见 §四） |
| **现在能不能真跑一条直播** | ❌ **缺一个真实源** | 强：本机**没有** ffmpeg / VLC / OBS |
| **要不要先补环境再排期** | ✅ **要** | 否则会重演 `P-052`（把环境缺口当成产品缺陷） |

**一句话**：**播放端已经就绪（协议在、`-directURL` 原样把 URL 交给内核、真机局域网也通了），
缺的只有"推流那一端"。** 补一个本机 RTSP 源（`mediamtx` + `ffmpeg`，一次性环境安装）就能开始 `P6-T1`。

## 一、事实 1：产物能力（两条**互相独立**的证据）

### 1.1 产物里的协议名（弱证据）

```
$ strings -a MPV/Library/Libmpv.xcframework/ios-arm64/Libmpv.framework/Libmpv \
    | grep -xE 'rtsp|rtsps|rtmp|rtmps|rtmpt|rtmpe|http|https|m3u8' | sort -u
http  https  m3u8  rtmp  rtmpe  rtmps  rtmpt  rtsp  rtsps
```

⚠️ **这条只能当线索**：字符串可能来自长名字或别的表。**不能据此下结论**（同 `P-050` 的教训：
"看起来有"与"真的被注册"是两件事）。

### 1.2 运行时探针（强证据 —— **内核真的走到哪一步**）

在 `MPVKernelTests`（**已有的 serialized 套件内**，`P-045`）临时加一个探针，
把 `rtsp://127.0.0.1:8554/probe` 与 `rtmp://127.0.0.1:1935/probe` 交给内核，收内核日志：

```
=== PROBE rtsp://127.0.0.1:8554/probe ===
[mpv/stream_callback] Opening rtsp://127.0.0.1:8554/probe
[mpv/ffmpeg] tcp: Connection to tcp://127.0.0.1:8554?timeout=0 failed: Connection refused
=== PROBE rtmp://127.0.0.1:1935/probe ===
[mpv/ffmpeg] rtmp: Cannot open connection tcp://127.0.0.1:1935?tcp_nodelay=0
[mpv/ffmpeg] tcp: Connection to tcp://127.0.0.1:1935?tcp_nodelay=0 failed: Connection refused
[mpv/stream] Failed to open rtmp://127.0.0.1:1935/probe.
```

**判据（为什么这条强）**：三种失败形态长得完全不一样 ——

| 失败点 | 日志长相 | 含义 |
| --- | --- | --- |
| **协议没编入** | `Protocol not found` / 立刻 `Failed to open`，**不尝试连接** | 产物缺协议 |
| **协议在、没人听** | 走到 `tcp://…:8554?timeout=0` 才报 `Connection refused` | ✅ **本次就是这个** |
| 协议在、路径被拦 | `Connection timed out` | 网络/策略问题 |

⇒ 两条 URL **都走到了 TCP 连接阶段**，而且是 **ffmpeg 自己的实现**（RTSP 的 TCP 隧道 URL 带
`?timeout=0`；RTMP 的报错前缀是 `rtmp:`）。**本机没有服务在听，所以"被拒"正是预期的成功形态。**

> 探针用完即撤（它不是产品测试，且 `P-033` 要求夹具确定性）。
> 复用方式：把上面这段贴回 `MPVKernelTests` 再跑一次即可（`enableLogging` + `load` + 4 秒）。

## 二、事实 2：**没有参考实现可抄**（原来的判断，现在核实过了）

```
$ grep -rnE 'rtsp|rtmp' vendor/ksplayer/Sources/
vendor/ksplayer/Sources/MPVPlayer/MPVOption.swift:1072:  /** --rtsp-transport=<lavf|udp|udp_multicast|tcp|http> */
vendor/ksplayer/Sources/MPVPlayer/MPVOption.swift:1073:  static let rtspTransport = "rtsp-transport"
```

**全部命中就是这两行** —— 一个选项名声明，**没有任何实现、策略或延迟处理**。
`docs/01` §7.2 的判断（"KSPlayer 文档只说了支持 RTMP、RTSP，没有实现细节"）**成立**。

⇒ `Phase 6` **没有可抄的路径**：策略得我们自己定、指标得我们自己设计。
这与 `P4-T3`（字幕自绘）不同 —— 那里至少有个明确的两选一；这里连"选什么"都要先想。

## 三、事实 3：低延迟候选参数（**名字都在产物里**）

| 选项 | 作用（预期） |
| --- | --- |
| `cache-secs` | 缓存时长上限；`0` = 不缓存（直播低延迟的关键一手） |
| `cache-pause` | 缓存不足时是否暂停（直播下常要关掉） |
| `demuxer-readahead-secs` | 解复用预读时长 |
| `demuxer-lavf-o` | 透传 ffmpeg 的 AVOption（`rtsp_transport=tcp` / `stimeout` …） |
| `rtsp-transport` | `lavf / udp / udp_multicast / tcp / http`（mpv 自己的 RTSP 开关） |
| `untimed` | 不计时播放（**只适用于固定帧率、明确不要同步的场景**，风险自担） |
| `video-sync` | `audio`（默认）/ `display-resample` / `desync` … 追帧与音画同步的核心 |
| `network-timeout` | 已有（30 s） |
| `hls-bitrate` | HLS 变体选择（**与 `Phase 5` 那条"可切清晰度"相关**） |
| `lavfi-complex` | 滤镜图（与低延迟无关，顺带确认可用） |
| `demuxer-max-bytes` | 已有（64 MiB） |

**证据**：逐个 `strings | grep -cxF <名字>` 均为 **1**（在产物里各出现一次 ⇒ 选项已注册）。

⚠️ **但这只是"名字在"**：值域、默认值、**是否真的把延迟降下来**，全都要实测。
本项目的判据一贯是 **"我设了 ≠ 它认了"**（`P-050`）—— 现有 `rejectedOptions` +
`testEveryConfiguredOptionIsAcceptedByMPV` 就是干这个的，`P6-T1` 应当沿用这条机制。

## 四、要验它，缺什么（**环境登记**）

| 需要 | 现状 | 说明 |
| --- | --- | --- |
| **推流器**（把画面变成 RTSP/RTMP 流） | ❌ **没有** | 本机 `ffmpeg` / `VLC` / `OBS` **都没装** |
| **RTSP/RTMP 服务器** | ❌ 没有 | `mediamtx`（单文件 Go 程序）是首选；`ffmpeg -rtsp_flags listen` 也能顶 |
| 播放端 | ✅ **已就绪** | `-directURL` **原样**把 URL 交给内核（不下载、不转码）⇒ **不需要改一行代码就能测直播** |
| 真机 ↔ 宿主网络 | ✅ 已通 | 本轮打通（`192.168.2.217:8765`，见 `docs/12`） |
| 延迟指标 | ⬜ **待设计** | 见 §五 |

> **安装是一次性环境动作**（`brew install mediamtx ffmpeg`），**不写进仓库、不算项目机器**（铁律 1）。
> 是否现在装 → 待董事长定。

## 五、建议的票面拆分（供董事长裁）

| 票 | 内容 | 规模 | 可测性 |
| --- | --- | --- | --- |
| `P6-T1` | **直播打通**：本机源 → 真机 `-directURL rtsp://…` → 出画 + 出声 + 时间推进 | M | **强**：复用 `-directURL` + 每秒 `[status]`（本轮刚建好的取证通道） |
| `P6-T2` | **延迟测量与调优**：给出**可量化**的端到端延迟指标 | L | **弱**（要设计）：怎么定义"延迟"是这票的主要工作 |
| `P6-T3`（新） | 低延迟参数**落地**：哪些选项、什么值、代价是什么（**逐一实测**而非照抄文档） | M | 强：沿用 `rejectedOptions` 机制 |

**延迟指标的设计候选**（`P6-T2` 的主要工作量，先登记不结论）：

1. **烧时间码**：推流侧把墙钟时间烧进画面 → 播放侧截图 → 与当前墙钟相减。
   优点：像素级可证；缺点：需要 `drawtext`（ffmpeg 全量版）。
2. **秒表对照**：手机屏幕与推流端同框录屏，数帧差。优点：零依赖；缺点：不够严谨。
3. **页面内指标**：读 mpv 的 `demuxer-cache-time` / `time-pos` 与推流端 PTS 比较。
   优点：自动化；缺点：**只覆盖播放器内部**，不含网络与编码。

⚠️ 无论选哪种，**"延迟"必须写清是端到端还是播放器内部** —— 否则数字之间不可比。

## 六、未定与风险

| 项 | 说明 |
| --- | --- |
| iOS 后台音频 | 直播常要求后台出声 ⇒ 需要 background audio 能力与音频会话配置（**属产品约束**，需董事长定） |
| UDP / 组播在 iOS 上的可行性 | `rtsp-transport=udp` 在 iOS 上受网络策略影响；`tcp` 最稳但要实测 |
| 是否需要"低延迟模式"开关 | 低延迟与省电/画质互相拉扯 ⇒ **要不要做成用户可见的开关**属产品决策 |
| 与 `Phase 5` 遗留的关系 | §二 的「可切清晰度」需要一个 **HLS 多码率源**；`hls-bitrate` 已在产物里，**同一批环境安装可以一起解决** |
| `cache-secs=0` 的代价 | 不缓存 ⇒ 网络抖动直接打到画面上。**"更低的延迟"与"更抗抖"是对立的**，不能既要又要 |

---

## 七、结论一句话

**`P6-T0` 给出的结论是：技术上没有拦路虎（协议已在产物里、播放端已就绪），
真正的缺口是"没有一个真实直播源"** —— 而那是**环境**而不是产品。
⇒ 建议：**先补环境（一次性），再排 `P6-T1`**；
并在此之前**明确 `G5`「可切清晰度」那条是否算 `Phase 5` 的欠账**（它同样是"缺一个源"）。
