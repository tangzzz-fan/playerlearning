## 二、逐条展开

### A1 · 定位：自用为主，目标上架 App Store

**理由**：开发期（M0–M3）不分发 ⇒ **许可义务完全不触发**；产品成形后再走分发，此时以公司号上架（`Apple Distribution: TIANJU DIHE (SUZHOU) DATA CO., LTD.` / `3GMJYX32U9`）。

**⚠️ 依赖「不分发 ⇒ 零义务」这句话的法律依据**：GPLv3 §2 原文 —— *"You may make, run and propagate covered works that you do not convey, **without conditions**"*。LGPL 同理。**这不是钻空子，是许可证的设计。**

**被否**（2026-10-13 更新）：

| 被否方案 | 为什么否 |
| --- | --- |
| ~~自用 / 内部工具，不对外分发~~ | **已被你自己推翻** —— 上架是确定的 |
| 开源分发 | 与上架目标冲突；且会引入 LGPL 的对应源码义务（虽然我们本来就要交） |
| 纯学习练手 | 与 A2「全都要」不兼容 |

**连带影响（必须一并接受）**：

1. **`vendor/ksplayer/` 只能读思想，不得抄代码文本** —— 原 A1 的理由（"授权约束全部解除，参考实现可放心研读借鉴"）**已失效**。`vendor/ksplayer/NOTICE.md` 已写明：要么移除 `vendor/`，要么整体遵守 GPL。**只发 `docs/` 不发 `vendor/` 则不受影响**；但我们的产品代码一旦与它混同，整包被拖入 GPL。
2. **合规责任人主体 = 公司**（D2 决定的连带含义，见 `docs/04` §4）。

---

### A2 · 内容：全都要（本地文件 + 网络点播 + 直播）

**理由**：用户明确要求。

**必须同时接受的代价**（这是本次拷问里最大的隐形成本项）：

| 要的能力 | 必须造的部分 | 参考实现是否趟过 |
| --- | --- | --- |
| 本地文件（mkv / 多编码 / 字幕） | FFmpeg 解封装 + 解码 + 渲染 + 同步 | ✅ `KSMEPlayer`（但**闭源**，只有文档） |
| 网络点播 HLS / mp4 | 缓存与清晰度切换 | ✅ `KSAVPlayer` |
| 直播 RTMP / RTSP / 低延迟 | 低延迟缓冲策略、时钟追帧 | ⚠️ 文档只提一句，**没有实现细节** |
| 三样共存 | 内核分派 | ✅ `playerTypes` 注册表 |

**结论**："全都要"已不是"一个播放器"，而是"一次完整播放器重建"。因此**必须设第一期最小闭环**把范围钉死。

> ⚠️ 这条决策与 `README.md` 中"第一期 iOS 最小闭环"直接冲突的风险最高，靠 F/C/D 三条的"先跑通一条链路"来化解。

### A3 · 平台：iOS 优先 → macOS 跟进

**理由**：用户选择。

**必须接受的硬约束**（2026-10-13 实测更新 —— 原表里「无 iOS 真机 slice」这一条是**参考实现**的限制，与我们已无关）：

| 想做的事 | 状态 |
| --- | --- |
| iOS **模拟器**开发调试 | ✅ 自建产物含 `ios-arm64_x86_64-simulator` |
| iOS **真机**运行 | ✅ 自建产物含 `ios-arm64`，**已真机验证出画面**（`docs/07`） |
| 拿到内核「源码」 | ⚠️ mpv 是开源上游；**mpvkit 的 3 个 patch**（含 `wid` 通路）需一并纳入合规材料（`P0-T6`） |

### B1 · 内核：libmpv 单内核（**2026-10-13 复核，维持**）

**理由**：目标是"全都要 + iOS 优先"，这两者叠加时，**重写解码管线是纯成本、不是收益**。libmpv 白送全格式 / 直播 / 字幕 / 硬解，要写的只剩 UI 层 + 渲染绑定。

**复核结论（上架决定之后重新问了一遍「还成立吗」）**：**成立**。因为 libmpv **本身**不构成上架障碍 —— 构成障碍的是「GPL 构建」与「静态链接」这两件事，而它们都已经通过 B2 的产物选择解决掉了。

> **这条是本项目最容易被误解的一点**：见 §三「分发口径」的判定树。

**被否 1**：AVPlayer + 自研 FFmpeg 双内核（照抄参考实现）。
**为什么否**：额外收益（AirPlay / DRM / 系统 HDR）不是刚需，额外成本是"重写 5 线程解码管线"。

**被否 2**：只用 AVPlayer。**为什么否**：mkv / 全格式正是这个工具的核心价值。

**被否 3**：单自研 FFmpeg 内核（不搞分派）。**为什么否**：libmpv 就是这条路的成熟成品，自己造不如用。

---

### B2 · 产物来源：**自建动态 LGPL-2.1 产物**

**理由**：现成的两个产物**恰好错配** —— 没有「动态 + LGPL」的组合可用：

| 现成产物 | 动态？ | LGPL？ | 结论 |
| --- | --- | --- | --- |
| `kingslay/FFmpegKit` 的 `libmpv.framework` | ✓（带 `_CodeSignature`） | ✗ **GPL 构建**（`--enable-version3`） | 与上架冲突 |
| `mpvkit/MPVKit` 的 `Libmpv.xcframework` | ✗ **`ar archive`（静态）** | ✓（`-Dgpl=false`） | 静态 ⇒ LGPL 的 re-linking 路径不成立 |

⇒ **必须自建**。做法：改 mpvkit 的构建脚本产出**动态** framework，并把 TLS 依赖链从 GnuTLS 换成系统 SecureTransport，从而把许可从 LGPLv3 压回 **LGPL-2.1**。

**已完成（2026-10-13，见 [`docs/07`](07-P0-T5b验证报告.md)）**：

| 项 | 实测结果 |
| --- | --- |
| 产物 | `Libmpv.xcframework`（104 MB）· `ios-arm64` + `ios-arm64_x86_64-simulator` |
| 类型 | 动态 framework，`install_name` = `@rpath/Libmpv.framework/Libmpv` |
| 许可 | **7 个 FFmpeg 库全部自报 `LGPL version 2.1 or later`** |
| 自包含 | `otool -L` 只有系统 framework；**零个** `libav*` / `libgnutls*` |
| 链入 | 21 个静态库，**gnutls / nettle / gmp / hogweed 命中 0** |
| 端到端 | 模拟器 + **真机**播本地 mkv 出画面 + PGS 字幕 |

**构建方式归档**：[`spike/p0-t5b-lgpl-dynamic-build/`](../spike/p0-t5b-lgpl-dynamic-build/)（`01-build-changes.patch` / `build.sh` / `postprocess-framework.sh` / `build-evidence.md`）。

**架构上的一个附带好处**：只有 `libmpv` 是动态库，FFmpeg 与其 20 个依赖**静态链进它** ⇒ **LGPL 视角「可替换的库」只有一个**，合规叙述远比「多库动态化」干净。

**未被否的**：自建 xcframework 原是"被否"项（理由：周期最长），**现已成为选定方案** —— 因为上架这个前提把它的"必要性"从可选变成必需。

### B3 · 抽象：第一天立边界，只实现一个内核

**理由**：参考实现的历史是**最强的证据** —— `MPVPlayer`（libmpv 内核）是 **2024-05-02** 才加入的，距离双内核设计已很久，而它往 `playerTypes` 注册表里塞第三个内核时，**上层一行没改**。

⇒ **抽象要早，实现要晚。** 现在立一个协议边界 + 一个实现，成本几乎为零；若把 mpv 的 API 直接铺到 UI 层，将来加腿就是重构。

**验证形式**（从参考实现的 `.swiftinterface` 实测得到的设计参照）：

```swift
public static var playerTypes: [any MediaPlayerProtocol.Type]      // 注册表
public static var firstPlayerType: any MediaPlayerProtocol.Type    // 首选
public static var secondPlayerType: (any MediaPlayerProtocol.Type)? // 备选 / fallback
public static var playerLayerType: KSPlayerLayer.Type
```

> **补充（2026-10-13）**：从 `Sources/MPVPlayer/KSMPVPlayer.swift`（453 行，开源）可以**反推出 `MediaPlayerProtocol` 的完整形状** —— 一个协议的实现必须实现它的全部 required 方法。其中「空实现反推」尤其有用：`configPIP()` 函数体为空 ⇒ **画中画是 AVPlayer 内核专属能力**，与显式放弃清单互相印证。

### B4 · 渲染接入：`wid` 嵌入 + 抽一层出口（**配置已实测**）

**参考实现的做法**（`vendor/ksplayer/Sources/MPVPlayer/MPVHandle.swift` 实测原文）：

```swift
var layer = metalView.layer
mpv_set_option(mpv, MPVOption.Window.wid, MPV_FORMAT_INT64, &layer)   // 把 CAMetalLayer 交给 mpv
setOption(name: MPVOption.Video.vo, value: "gpu-next")
setOption(name: MPVOption.GPURendererOptions.gpuApi, value: "vulkan")
setOption(name: MPVOption.GPURendererOptions.gpuContext, value: "moltenvk")
setOption(name: MPVOption.Video.hwdec, value: "videotoolbox")
```

| 路线 | 你写什么 | 拿到什么 | 代价 |
| --- | --- | --- | --- |
| **`wid` 窗口嵌入**（选定） | 一个带 `CAMetalLayer` 的 View，约 20 行 | 画面、字幕（含 ASS 特效）、色调映射、缩放全由 mpv 负责 | 多一层 **MoltenVK**；渲染细节不可控 |
| libmpv render API | 自己写 Metal draw loop（`mpv_render_context`） | 完全可控：全景 / VR / 自定义滤镜 / 与自家 UI 合成 / **无 MoltenVK** | 渲染循环、色彩空间、字幕叠加全自己管，工期显著变长 |

**关键提醒**：mpv 的 `gpu-api` **没有 metal 后端**，所以这条路必然经过 Vulkan-on-Metal（MoltenVK）。

**决策**：第一期走 `wid` 嵌入，但把"视频输出"收在一个协议后面 —— 若 MoltenVK 踩坑或将来要做全景/VR，只需换一个实现。

> ✅ **2026-10-13 实测：已双通**（模拟器 + 真机 iPhone 16 Pro）。关键配置与坑见 [`docs/06`](06-P0-T5a技术验证报告.md) / [`docs/07`](07-P0-T5b验证报告.md)。其中 `MetalLayer.swift` 解决了「MoltenVK 把 drawableSize 设成 1×1 导致闪烁」的问题 —— **必须照抄这个修复**。

### C · 工程骨架：SPM 双 target + XcodeGen（**2026-10-13 修订：拆出独立 MPV 包**）

```
playerlearning/                    ← 仓库根
├── Package.swift                  ← 根包 PlayerStack：PlayerCore / PlayerUI（iOS 17 / macOS 14）
├── Sources/
│   ├── PlayerCore/                ← 内核边界、状态机、时间模型（禁止 import SwiftUI/UIKit/AppKit）
│   └── PlayerUI/                  ← SwiftUI 视图、控制层、手势
├── Tests/PlayerCoreTests/         ← 纯逻辑单测 + 集成测试（跑在 macOS，快）
├── Tools/                         ← gate.sh（G1 门禁）· mutation_check.py · stage-libmpv.sh
├── MPV/                           ← ⚠️ 独立包 PlayerMPV：libmpv 适配器（只在 iOS 上编译）
│   ├── Package.swift              ← 依赖根包 + Library/Libmpv.xcframework
│   ├── Sources/PlayerMPV/         ← MPVKernel（`#if canImport(Libmpv)` 守卫）
│   └── Library/                   ← 产物落点（gitignored，由 stage-libmpv.sh 产出）
└── Demo/
    └── project.yml → xcodegen     ← app shell
```

**理由**：① 逼你把内核和 UI **物理隔开**（这是保住可测性的唯一手段）；② mac / iOS 共用同一个包，符合"A3 iOS 优先 → macOS 跟进"；③ 与既有 XcodeGen 习惯一致。

#### ⚠️ 修订：为什么 libmpv 接入**不在** `PlayerCore` 里（2026-10-13 董事长拍板）

> **原设计**把「libmpv 接入」放在 `PlayerCore` 内。**实测推翻了它**：

| 事实（探针实测，非推测） | 后果 |
| --- | --- |
| 自建产物**只有 iOS 切片**（`ios-arm64` / `ios-arm64-x86_64-simulator`），**无 macOS 切片** | 若接线进 `PlayerCore`，**根包的 `swift test`（跑在 macOS）会直接挂** |
| **SPM 会校验 `binaryTarget` 的路径是否存在，与平台条件无关** | 产物是 gitignored 的 ⇒ **新克隆的 `swift build`/`swift test` 必失败** |

⇒ 两条路都指向同一个结论：**适配器必须与根包解耦**。

**选定方案：独立包 `MPV/`**（备选是"再构建一套 macOS 切片"，被否 —— 代价是 20–30 分钟构建 + 产物翻倍，而 macOS 上跑 mpv 适配器单测**意义有限**：真实管线是另一套，且 macOS 属 P7）。

| 收益 | 代价 |
| --- | --- |
| 根包**新克隆即可 `swift test`**；`./Tools/gate.sh` 原样可用 | `MPV/` 需先 `Tools/stage-libmpv.sh` 才能构建（文档化为前置条件） |
| 适配器只在它唯一能跑的平台（iOS）上构建 | 适配器测试须跑 iOS 模拟器，不能用 macOS 快循环 |
| libmpv 的链接复杂度被隔离在一个包里 | 产物 104 MB 落 `MPV/Library/`（gitignored） |

**已实现的隔离手法**（都经实测验证）：
1. `MPV/Package.swift` 用 `.package(name: "PlayerStack", path: "..")` **显式命名**路径依赖 —— 避免耦合到仓库目录名（见 `PITFALLS` `P-021`）
2. libmpv 依赖加 `condition: .when(platforms: [.iOS])` + 源码用 `#if canImport(Libmpv)` 守卫 ⇒ **macOS 上该文件编译为空**，`swift build` 通过
3. mpv 句柄的所有权交给一个 `private final class` 持有者（见 `P-022`），actor 的 `deinit` 不碰非 Sendable 状态

**理由（原）**：① 逼你把内核和 UI **物理隔开**；② mac / iOS 共用同一个包；③ 与既有 XcodeGen 习惯一致。

**被否**：单个 app 工程（内核与 UI 无编译期隔离）／Xcode 工程 + 内嵌本地包（工程文件更绕）／**fork 参考仓库改**。

**为什么否决 fork**：内核是闭源二进制且**无 iOS 真机 slice**，一旦要改内核行为就撞墙；UI 那侧是两个 2000+ 行巨型文件，读懂的代价高于自己写。（与授权无关 —— 即使不考虑 GPL，fork 也不划算。）

### D · UI：纯 SwiftUI 一套，第一期只做 5 件

**第一期功能面**：① 播放/暂停 ② 进度条 + seek ③ 时间显示 ④ 全屏与旋转 ⑤ 外挂字幕开关。

**全部推后**：倍速、音轨/字幕轨切换、清晰度、设置面板、手势调亮度音量、画中画。
（理由：它们不验证任何风险，只是延长"看到画面"的时间。）

**为什么坚持纯 SwiftUI**：参考实现同一个播放器 UI 写了**三套**（`IOSVideoPlayerView` UIKit 2116 行 + `MacVideoPlayerView` AppKit 212 行 + `SwiftUI/` 16 文件）。**这是它 13k 行 UI 代码膨胀的主因**，可直接绕开。

**时间/进度推送**：一开始就用 **0.2–1 s 粒度 + `AsyncStream`**，不要复制 `ControllerTimeModel` 那个毫秒级 `@Published` 的坑（作者自己在注释里写了：「这是一个频繁变化的model。View要少用这个」）。

**值得参考**（体积小、职责单一）：`GestureView`（手势）、`PlayerSlider`（进度条拖拽）、`SeekView`（seek 预览）、`KSMenu`、`VideoControllerView` 的布局骨架。
**不值得参考**：`SettingsView`（2147 行）、`IOSVideoPlayerView`（2116 行）。

### F · 测试边界：fake 内核 + 纯逻辑单测

**核心抓手**：只要 `PlayerCore` **不 import SwiftUI/UIKit**，并且**把 mpv 调用收在一个可替换的适配器后面**，就获得了可注入 fake 内核的缝 —— 于是状态机、seek、时间轴、字幕解析、轨道切换**全部可以在没有 libmpv、没有硬件的情况下单测**，且能跑 mutation testing（因为它没有 I/O）。

**测试对象（可测清单）**：

| 层 | 可测内容 |
| --- | --- |
| 资源与配置 | URL / 多清晰度 / header / 选项解析 |
| 状态机 | `idle → preparing → readyToPlay → playing → paused → finished` 的迁移与非法迁移 |
| 时间轴 | seek 目标钳制、playableTime 边界、total==0 的退化处理 |
| 字幕 | SRT / ASS 解析、编码探测、按 PTS 查帧 |
| 轨道 | 音轨/字幕轨切换的模型映射 |
| mpv 适配器 | 属性 ↔ 模型映射（用 fake，不打真 mpv） |

**推后**：CI 里跑真文件的集成测试。理由：在内核稳定前它只会带来 flaky，不会带来信心。

**被否**：只测纯函数不做协议抽象（状态机与 UI 链路无覆盖）／先不写测试（与既有 TDD 纪律相背）。

## 三、分发口径（**2026-10-13 新增 · 本文最重要的一节**）

> 这一节的存在原因是：**上架是确定的**，而「许可只在分发时触发」。把义务写在一处，半年后不会有人因为"反正是自用"就把包发出去了。

### 3.1 判定树：什么决定能不能上架

```
能上架吗？
├─ libmpv 是哪种构建？
│   ├─ GPL 构建（--enable-version3 / -Dgpl=true）  → ✗ 整包被传染成 GPLv3
│   └─ LGPL 构建（-Dgpl=false + FFmpeg 关 version3）→ ✓ 继续下一问
└─ 动态还是静态链接？
    ├─ 静态  → ✗ 只能退到「交出可重链接材料」⇒ 等于要开源你的 App
    └─ 动态  → ⚠️ 业界通行达标方式，但 iOS 上有灰区（见 3.3）
```

**我们所在的位置：LGPL + 动态。** 两个条件都已由 `P0-T5b` 实测满足。

### 3.2 我们产物的许可结论

| 项 | 结论 |
| --- | --- |
| 产物许可 | **LGPL-2.1 or later**（不是 GPLv3，也不是 LGPLv3） |
| 为什么是 2.1 而不是 3 | 不启用 FFmpeg 的 `--enable-version3`；**并把 TLS 链从 GnuTLS→nettle→gmp（三者同为 LGPLv3+）换成系统 SecureTransport** ⇒ v3 依赖链消失 |

> ⚠️ **2026-10-17 校（原文保留，补精确说法）**：上文"三者同为 LGPLv3+"**过宽** ——
> `gnutls` 自身是 **LGPL-2.1+**，把 v3 带进来的是它的依赖 **`nettle` / `gmp`（LGPLv3+ / GPLv2+，
> 在 FFmpeg 的 `EXTERNAL_LIBRARY_VERSION3_LIST` 里）**。决策与结论不变（**换掉整条链**），
> 但"谁带的 v3"要说准 —— 依据见 [`docs/07`](07-P0-T5b验证报告.md) §3.2 的报错原文与传导链表。
| 为什么要避开 LGPLv3 | LGPLv3 = GPLv3 + 附加许可，因此**继承了 GPLv3 §3（反技术措施）与 §6/§4(e) 的 Installation Information**。LGPL-2.1 **没有这两条**，对 iOS 友好得多 |
| 分发时要交什么 | ① 库的**对应源码**（含 mpvkit 对 mpv 的 3 个 patch）；② 许可文本与说明；③ 保证「用户可以替换库」（尽力合规，见 3.3） |
| 要付钱给谁 | **不用付任何人**。kingslay 不用付（GPL/LGPL 已授权你，他的付费档是卖给"不想守"的人的）；mpv / FFmpeg 作者不用付。**唯一要留意的钱是编解码专利池**（H.264/HEVC，商业分发时触发）—— 与开源许可无关 |

### 3.3 ⚠️ 灰区：iOS 上「用户可替换库」实质不成立

**这是本项目唯一的许可级风险，必须写在最显眼处。**

- LGPL 合规的枢纽是「**re-linking 必须可能**」。
- 但 App Store 下发的 App 是 **FairPlay 加密 + Apple 签名**的。用户就算拿到你提供的库源码，也**无法替换 App 内的那份**（那需要重签整个 App，加密包做不到）。
- ⇒ **动态 framework 是必要条件，不是充分条件。** 我们能做的是业界标准那一套「**尽力合规**」（动态库 + 提供库源码 + 提供可重链接材料 + 许可文本）。
- **真实的风险来源不是 Apple 审核，是上游 contributor 投诉** —— VLC 2011 年下架就是权利人投诉触发的（Rémi Denis-Courmont），不是 Apple 主动执法。这既解释了为什么现实中大量含 LGPL 库的 App 好端端在架，也解释了为什么这件事永远是灰的。
- **没有找到「LGPL 库因许可被 App Store 下架」的案例**（VLC 那次是 GPL + 项目内 contributor 对第三方移植的投诉）。但「没查到」不等于「不存在」。

⇒ **对外表述纪律：只能宣称「已尽力合规」，不得宣称「已确保合规」。**

### 3.4 三条红线的反面（什么会让我们瞬间不可上架）

| 若发生 | 后果 |
| --- | --- |
| 产物改回 **GPL 构建**（`-Dgpl=true` / 恢复 `--enable-version3`） | 整包被传染成 GPLv3 ⇒ App Store 实质不可行 |
| 产物改成**静态**链接 | 只能交「可重链接材料」⇒ 等于要开源 App |
| 把 `vendor/ksplayer/` 的**代码文本**抄进产品代码 | 触发 GPLv3 传染（`docs/01` 只可借思想） |

## 四、显式放弃清单

选了 libmpv 单内核，等于**主动放弃**以下能力。**这不是遗漏，是决策** —— 半年后不要把它当成 bug：

| 放弃的能力 | 影响 | 证据/状态 |
| --- | --- | --- |
| **AirPlay** | 不能投到 Apple TV / HomePod | 已知 |
| **FairPlay DRM** | 不能播受保护内容（Apple TV+ / Netflix 等） | 已知 |
| **原生画中画（PiP）** | `AVPictureInPictureController` 依赖 AVPlayer 链路 | ✅ **已有实证**：`KSMPVPlayer.configPIP()` 是空实现 ⇒ PiP 为 AVPlayer 内核专属 |
| **系统 HDR 通路** | HDR 依赖 mpv 自己的色调映射，不走系统 EDR | 已知 |
| **低功耗** | 不经系统解码/渲染管线，功耗高于 AVPlayer | 已知 |
| **「不含 FFmpeg 的精简构建」** | 体积大（产物 104 MB / 单切片更小）。授权影响**已收敛**：走 LGPL-2.1 + 动态 ⇒ 代价是「要交对应源码」，不是「不能上架」 | 见 §三 |

> **注意**：**「iOS App Store 上架」不在本清单里** —— 它是被选定的目标，不是被放弃的东西（`docs/04` §7 早期版本曾把它列为"建议放弃"，2026-10-13 拍板选项 A 后撤销）。

## 七、由决策推出的施工约束（硬性）

1. **`PlayerCore` 禁止 import SwiftUI / UIKit / AppKit** —— 违反即失去可测性。
2. **mpv 调用只允许出现在适配器实现里** —— 不允许泄漏到 `PlayerUI`。
3. **视频输出走协议**，第一期实现为 `wid` 嵌入。
4. **工程结构走 SPM 双 target**，Demo 用 `project.yml` + xcodegen 生成。
5. **进度/时间推送一律 0.2–1 s 粒度**，禁止毫秒级 `@Published`。
6. **不引入 submodule 装大二进制依赖**；`Package.swift` 保持声明式，禁用 `unsafeFlags`。
7. **每完成一个可验证链路即提交**，与既有 ticket 节奏一致。
8. **libmpv 产物必须是「动态 + LGPL 构建」**，且**构建脚本化、可原样重跑**（LGPL 要交"构建方式"，不能是"我在 Xcode 里点了两下"产出的包）。
9. **产物二进制不入 git**（104 MB）；入库的是**构建方式**（patch + 脚本 + 证据），产物由脚本产出。
10. **`vendor/ksplayer/` 只可借思想，不得复制代码文本**（A1 反转后生效）。
11. **libmpv 接入只允许出现在 `MPV/` 独立包内** —— 根包（`PlayerCore`/`PlayerUI`）**不得**引用 libmpv（违反即毁掉根包的 `swift test` 快循环）。
12. **跨包引用一律用 `.package(name:path:)` + `.product(name:package:)`** —— 裸字符串（`.byName`）跨包不可靠，且只用 `path:` 会把仓库目录名耦合进 manifest（见 `PITFALLS` `P-021`）。
13. **C 资源的释放放进拥有所有权的引用类型的 `deinit`**，不依赖调用方记得调 cleanup（见 `P-022`）。
14. **测试一律用 Swift Testing**（`@Test` / `#expect` / `try #require` / `@Suite`），**不使用 XCTest**。
    触及 `CAMetalLayer` / Metal / 全局共享状态的套件必须显式 `@Suite(.serialized)` —— **Swift Testing 默认并行执行**。
    ⚠️ 换测试框架 = 换门禁管道：`gate.sh` 的计数解析、`mutation_check.py` 的超时策略必须同批改（见 `P-026`）。
15. **xcodegen 生成工程时必须显式声明 `schemes:`** —— xcodegen **默认不生成** scheme，没有 scheme 时
16. **验收标准 = 项目能正确运行 + `swift test` 全绿**（2026-10-14 董事长决定）。**不在项目里堆构建/门禁脚本** —— 之前 `Tools/` 里的 `gate.sh`（8 步）与 `mutation_check.py`（113 个变异体）合计 ≈950 行、一次 ≈7 分钟，**已经取消并删除**。理由与代价见 `docs/03` 的 📌。
17. **构建/测试环境用现成技能，不要自己包一层**：`~/.workbuddy/skills/{ios,macos}-build-test/scripts/*-run.sh` 已经封装了沙箱逃逸判据、自动挑模拟器、toybox shim 处理（`P-028`）与日志落文件。项目里各搓一份探针，正是「每轮都要临时试」的根源。
18. **端到端素材必须是真实视频**：自造片段只能证「链路通了」，它没有真实码流 / 音轨参数 / 容器结构，而这三样最容易出问题。素材**运行时下载**（不随仓库分发），离线时退回本地生成；**用哪一个是哪个必须打印出来**（退回兜底时断言照样绿，那不叫通过，那叫没测到）。推论：**素材参数（尺寸 / 采样率 / 时长）不许写死在断言里** —— 换素材就会假红。
    `xcodebuild -scheme` 与 CI 全都不可用（见 `Demo/project.yml`）。生成的 `.xcodeproj` **不入 git**，由 `xcodegen generate` 产出。
