# 自建播放器 · 决策记录

> 本文是一次**动手前的方案拷问**（grill-me）的结果。所有决策以「决策 → 理由 → 被否方案 → 为什么否」的形式记录，便于将来复盘时知道当时否决了什么、为什么。
>
> **背景**：要做一个类似 KSPlayer 的 mac / iOS 播放器。设计思想与参考实现评估见 [`01-KSPlayer-设计思想与整体评估.md`](01-KSPlayer-设计思想与整体评估.md)。
> **记录日期**：2026-10-13

---

## 一、决策总表

| 分支 | 决策 | 一句话理由 |
| --- | --- | --- |
| **A1 定位** | 自用 / 内部工具，**不对外分发** | 授权闸门解除 ⇒ 参考实现可放心借鉴 |
| **A2 内容** | 本地文件 + 网络点播 + 直播，**全都要** | 能力面拉满，但必须靠"第一期"把范围钉住 |
| **A3 平台** | **iOS 优先 → macOS 跟进** | 先啃最难的平台 |
| **B1 内核** | **libmpv 单内核** | 重写解码管线对自用场景是纯成本 |
| **B2 产物来源** | **`kingslay/FFmpegKit` 的 SPM 产物**（含 libmpv + MoltenVK） | 把"构建 FFmpeg"这件最容易吞掉数周的事往后推 |
| **B3 抽象** | 第一天立 `MediaPlayerProtocol` 式边界，**只实现一个内核** | 扩展点成本≈0，未来加腿不用重构 |
| **B4 渲染接入** | **`wid` 嵌入**（照抄参考实现），但视频输出**抽成可替换协议** | 让 mpv 自己画，省掉整条渲染管线 |
| **C 工程骨架** | **SPM 双 target**（`PlayerCore` / `PlayerUI`）+ XcodeGen 生成 Demo 工程 | 内核与 UI 编译期隔离 = 可测性的前提 |
| **D UI** | **纯 SwiftUI 一套**，第一期只做 5 件事 | 省掉"三套实现"的税 |
| **E 平台基线** | **iOS 17+ / macOS 14+ / Swift 6 严格并发** | 拿到 `@Observable`，不背双语言模式包袱 |
| **F 测试边界** | **fake 内核 + 纯逻辑单测**（可跑 mutation testing） | 无 I/O 才能快速重跑，mutation testing 才成立 |

## 二、逐条展开

### A1 · 定位：自用 / 内部工具，不对外分发

**理由**：授权约束全部解除 —— 参考实现的 GPL 源码可以放心研读借鉴；"能不能被别人当 SwiftPM 依赖消费"也降级为非需求（因此 `unsafeFlags`、二进制入库这类问题对我们"不必模仿但不致命"）。

**被否**：商业上架 App Store / 开源分发 / 纯学习练手。

---

### A2 · 内容：全都要（本地文件 + 网络点播 + 直播）

**理由**：用户明确要求。

**必须同时接受的代价**（这是本次拷问里最大的隐形成本项）：

| 要的能力 | 必须造的部分 | 参考实现是否趟过 |
| --- | --- | --- |
| 本地文件（mkv / 多编码 / 字幕） | FFmpeg 解封装 + 解码 + 渲染 + 同步 | ✅ `KSMEPlayer`（但**闭源**，只有文档） |
| 网络点播 HLS / mp4 | 缓存与清晰度切换 | ✅ `KSAVPlayer` |
| 直播 RTMP / RTSP / 低延迟 | 低延迟缓冲策略、时钟追帧 | ⚠️ 文档只提一句，**没有实现细节** |
| 三样共存 | 内核分派 | ✅ `playerTypes` 注册表 |

**结论**："全都要"已不是"一个播放器"，而是"一次完整播放器重建"。因此**必须设第一期最小闭环**把范围钉死。

> ⚠️ 这条决策与 `README.md` 中"第一期 iOS 最小闭环"直接冲突的风险最高，靠 F/C/D 三条的"先跑通一条链路"来化解。

---

### A3 · 平台：iOS 优先 → macOS 跟进

**理由**：用户选择（不是最初推荐；推荐的是 mac 优先，因为开发迭代最快、且参考实现的 GPL 二进制恰好只给 macOS slice）。

**必须接受的硬约束**（实测事实）：

| 想做的事 | 参考实现能否帮忙 |
| --- | --- |
| iOS **模拟器**开发调试 | ✅ 有 `ios-arm64_x86_64-simulator` slice |
| iOS **真机**运行 | ❌ **无 `ios-arm64` slice** |
| 拿到自研内核源码 | ❌ 闭源二进制 |

⇒ iOS 优先路线上**唯一的暗礁是真机**，见第六节。

---

### B1 · 内核：libmpv 单内核

**理由**：目标是"自用 + 全都要 + iOS 优先"，这三者叠加时，**重写解码管线是纯成本、不是收益**。libmpv 白送全格式 / 直播 / 字幕 / 硬解，要写的只剩 UI 层 + 渲染绑定。

**被否 1**：AVPlayer + 自研 FFmpeg 双内核（照抄参考实现）。
**为什么否**：对自用场景，那条路的额外收益（AirPlay / DRM / 系统 HDR）不是刚需，而额外成本是"重写 5 线程解码管线"。

**被否 2**：只用 AVPlayer。**为什么否**：mkv / 全格式这正是自用工具的核心价值。

**被否 3**：单自研 FFmpeg 内核（不搞分派）。**为什么否**：libmpv 就是这条路的成熟成品，自己造不如用。

---

### B2 · 产物来源：`kingslay/FFmpegKit` 的 SPM 产物

**理由**：不需要自建 FFmpeg 就能拿到 libmpv。自建的意义只在"我要特定 codec 组合 / 我要控制授权 / 我要 iOS 真机 slice"，而这三件事在第一期都不是瓶颈。

**被否**：自建 xcframework（周期最长，但一次到位）／依赖参考实现的二进制（拿不到 iOS 真机）／先用 AVPlayer 占位。

> **风险**：该包是否提供 **iOS 真机（`ios-arm64`）** 的 libmpv slice，无法离线验证，必须实测（见第六节）。

---

### B3 · 抽象：第一天立边界，只实现一个内核

**理由**：参考实现的历史是**最强的证据** —— `MPVPlayer`（libmpv 内核）是 **2024-05-02** 才加入的，距离双内核设计已很久，而它往 `playerTypes` 注册表里塞第三个内核时，**上层一行没改**。

⇒ **抽象要早，实现要晚。** 现在立一个协议边界 + 一个实现，成本几乎为零；若把 mpv 的 API 直接铺到 UI 层，将来加腿就是重构。

**验证形式**（从参考实现的 `.swiftinterface` 实测得到的设计参照）：

```swift
public static var playerTypes: [any MediaPlayerProtocol.Type]      // 注册表
public static var firstPlayerType: any MediaPlayerProtocol.Type    // 首选
public static var secondPlayerType: (any MediaPlayerProtocol.Type)? // 备选 / fallback
public static var playerLayerType: KSPlayerLayer.Type
```

---

### B4 · 渲染接入：`wid` 嵌入 + 抽一层出口

**参考实现的做法**（`Sources/MPVPlayer/MPVHandle.swift` 实测原文）：

```swift
var layer = metalView.layer
mpv_set_option(mpv, MPVOption.Window.wid, MPV_FORMAT_INT64, &layer)   // 把 CAMetalLayer 交给 mpv
setOption(name: MPVOption.Video.vo, value: "gpu-next")
setOption(name: MPVOption.GPURendererOptions.gpuApi, value: "vulkan")
setOption(name: MPVOption.GPURendererOptions.gpuContext, value: "moltenvk")
setOption(name: MPVOption.Video.hwdec, value: "videotoolbox")
```

| 路线 | 你写什么 | 拿到什么 | 代价 |
| --- | --- | --- | --- |
| **`wid` 窗口嵌入**（选定） | 一个带 `CAMetalLayer` 的 View，约 20 行 | 画面、字幕（含 ASS 特效）、色调映射、缩放全由 mpv 负责 | 多一层 **MoltenVK**；渲染细节不可控；iOS 稳定性需实测 |
| libmpv render API | 自己写 Metal draw loop（`mpv_render_context`） | 完全可控：全景 / VR / 自定义滤镜 / 与自家 UI 合成 / **无 MoltenVK** | 渲染循环、色彩空间、字幕叠加全自己管，工期显著变长 |

**关键提醒**：mpv 的 `gpu-api` **没有 metal 后端**，所以这条路必然经过 Vulkan-on-Metal（MoltenVK）。

**决策**：第一期走 `wid` 嵌入，但把"视频输出"收在一个协议后面 —— 若 MoltenVK 踩坑或将来要做全景/VR，只需换一个实现。

### C · 工程骨架：SPM 双 target + XcodeGen

```
YourPlayer/                        ← 仓库根
├── Package.swift                  ← Core / UI 两个 target，iOS + macOS 双平台
├── Sources/
│   ├── PlayerCore/                ← libmpv 接入、MediaPlayerProtocol、状态机（禁止 import SwiftUI/UIKit）
│   └── PlayerUI/                  ← SwiftUI 视图、控制层、手势
├── Demo/
│   └── project.yml → xcodegen     ← app shell，iOS + macOS 两个 target 共用同一包
└── Tests/PlayerCoreTests/
```

**理由**：① 逼你把内核和 UI **物理隔开**（这是保住可测性的唯一手段）；② mac / iOS 共用同一个包，符合"A3 iOS 优先 → macOS 跟进"；③ 与既有 XcodeGen 习惯一致。

**被否**：单个 app 工程（内核与 UI 无编译期隔离）／Xcode 工程 + 内嵌本地包（工程文件更绕）／**fork 参考仓库改**。

**为什么否决 fork**：对自用场景 GPL 确实没问题，但它救不了核心痛点 —— 内核是闭源二进制且**无 iOS 真机 slice**，一旦要改内核行为就撞墙；UI 那侧是两个 2000+ 行巨型文件，读懂的代价高于自己写。

---

### D · UI：纯 SwiftUI 一套，第一期只做 5 件

**第一期功能面**：① 播放/暂停 ② 进度条 + seek ③ 时间显示 ④ 全屏与旋转 ⑤ 外挂字幕开关。

**全部推后**：倍速、音轨/字幕轨切换、清晰度、设置面板、手势调亮度音量、画中画。
（理由：它们不验证任何风险，只是延长"看到画面"的时间。）

**为什么坚持纯 SwiftUI**：参考实现同一个播放器 UI 写了**三套**（`IOSVideoPlayerView` UIKit 2116 行 + `MacVideoPlayerView` AppKit 212 行 + `SwiftUI/` 16 文件），框架混用 SwiftUI 16 / UIKit 18 / AppKit 12 文件。**这是它 13k 行 UI 代码膨胀的主因**，可直接绕开。

**时间/进度推送**：一开始就用 **0.2–1 s 粒度 + `AsyncStream`**，不要复制 `ControllerTimeModel` 那个毫秒级 `@Published` 的坑（作者自己在注释里写了：「这是一个频繁变化的model。View要少用这个」）。

**值得参考**（体积小、职责单一）：`GestureView`（手势）、`PlayerSlider`（进度条拖拽）、`SeekView`（seek 预览）、`KSMenu`、`VideoControllerView` 的布局骨架。
**不值得参考**：`SettingsView`（2147 行）、`IOSVideoPlayerView`（2116 行）。

### E · 平台基线

| 项 | 取值 | 依据 |
| --- | --- | --- |
| iOS 最低版本 | **17.0** | 本机 SDK 为 iOS 27；17 这个地板不花任何代价，却能拿到 `@Observable`、现代 SwiftUI、Swift 6 并发 |
| macOS 最低版本 | **14.0+** | 与 iOS 17 同一代 API（`@Observable` 可用性对齐） |
| 语言模式 | **Swift 6 严格并发** | 参考实现还在 `[.v5, .v6]` 双模式过渡；从零开始没必要背这个包袱 |

> 数值来自本机环境（Xcode 27.0 / Swift 6.4 / iOS 27 SDK / 真机 iPhone 16 Pro），非推测。

### F · 测试边界：fake 内核 + 纯逻辑单测

**核心抓手**：只要 `PlayerCore` **不 import SwiftUI/UIKit**，并且**把 mpv 调用收在一个可替换的适配器后面**，就获得了可注入 fake 内核的缝 —— 于是状态机、seek、时间轴、字幕解析、轨道切换**全部可以在没有 libmpv、没有硬件的情况下单测**，且能跑 mutation testing（因为它没有 I/O）。

**测试对象（可测清单）**：

| 层 | 可测内容 |
| --- | --- |
| 资源与配置 | URL / 多清晰度 / header / 选项解析 |
| 状态机 | `idle → preparing → readyToPlay → playing → paused → finished` 的迁移与非法迁移 |
| 时间轴 | seek 目标钳制、playableTime 边界、total==0 的退化处理 |
| 字幕 | SRT / ASS 解析、编码探测、按 PTS 查帧 |
| 轨道 | 音轨/字幕轨切换的模型映射 |
| mpv 适配器 | 属性 ↔ 模型映射（用 fake，不打真 mpv） |

**推后**：CI 里跑真文件的集成测试。理由：在内核稳定前它只会带来 flaky，不会带来信心。

**被否**：只测纯函数不做协议抽象（状态机与 UI 链路无覆盖）／先不写测试（与既有 TDD 纪律相背）。

## 三、显式放弃清单

选了 libmpv 单内核，等于**主动放弃**以下能力。**这不是遗漏，是决策** —— 半年后不要把它当成 bug：

| 放弃的能力 | 影响 |
| --- | --- |
| **AirPlay** | 不能投到 Apple TV / HomePod |
| **FairPlay DRM** | 不能播受保护内容（Apple TV+ / Netflix 等） |
| **原生画中画（PiP）** | `AVPictureInPictureController` 依赖 AVPlayer 链路，需自建或不支持 |
| **系统 HDR 通路** | HDR 依赖 mpv 自己的色调映射，不走系统 EDR |
| **低功耗** | 不经系统解码/渲染管线，功耗高于 AVPlayer |
| **「不含 FFmpeg 的精简构建」** | 体积大、授权为 GPL/LGPL（自用不分发 ⇒ 无实际影响） |

## 四、待验证风险

| # | 风险 | 影响面 | 处置 |
| --- | --- | --- | --- |
| 1 | **`kingslay/FFmpegKit` 是否提供 iOS 真机（`ios-arm64`）的 libmpv slice** | **阻塞 iOS 真机交付** | 动手前先实测。若不提供 ⇒ 回退自建 xcframework |
| 2 | MoltenVK 在 iOS 上的稳定性与性能 | 阻塞画面 | `wid` 方案 + 抽象出口；若不可接受则切 libmpv render API |
| 3 | libmpv 的字幕渲染与我们自建 UI 的层级冲突（`wid` 嵌入时字幕由 mpv 画在最上层） | UI 设计约束 | 第一期接受；若需自绘字幕再切 render API |
| 4 | 直播低延迟策略无参考实现可抄 | A2「全都要」的第三块 | 明确推到后续期次，不在第一期范围 |

## 六、由决策推出的施工约束（硬性）

1. **`PlayerCore` 禁止 import SwiftUI / UIKit / AppKit** —— 违反即失去可测性。
2. **mpv 调用只允许出现在适配器实现里** —— 不允许泄漏到 `PlayerUI`。
3. **视频输出走协议**，第一期实现为 `wid` 嵌入。
4. **工程结构走 SPM 双 target**，Demo 用 `project.yml` + xcodegen 生成。
5. **进度/时间推送一律 0.2–1 s 粒度**，禁止毫秒级 `@Published`。
6. **不引入 submodule 装大二进制依赖**；`Package.swift` 保持声明式，禁用 `unsafeFlags`。
7. **每完成一个可验证链路即提交**，与既有 ticket 节奏一致。
