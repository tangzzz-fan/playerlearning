## 二、缺失的前置：装配层（本文最重要的结论）

**事实**：`PlayerStateMachine`、`PlayerTimeModel`、内核事件流，这三者**从未在生产路径上连接过** —— 唯一的连接发生在 `Tests/PlayerCoreTests/PlayerCoreIntegrationTests.swift`（测试代码，且是手写的 `PlayerCoreHarness` 结构体）。

**后果**：

| 后果 | 说明 |
| --- | --- |
| UI 拿不到任何状态 | `PlayerUI` 无从知道 `state` / 时间，Phase 3 无法开工 |
| 扇出无处安放 | `PITFALLS P-014` 已实测：**`AsyncStream` 只能有一个消费者**，两个 `for await` 会互相抢事件。所以"内核事件流 → 状态机 + 时间模型"必须有**唯一消费者**做扇出 |
| 钳制契约悬空 | 集成测试 `testSeekTargetIsClampedBeforeReachingKernel` 断言的是**契约**（"钳制后到达内核"），但没有生产代码履行它 |

**定义**：新增 `PlayerController` —— `PlayerCore` 内的 actor，对内是内核事件流的**唯一消费者**，对外是状态与时间的**唯一发布源**。

```
kernel.events() ──→ PlayerController（唯一消费者）
                      ├─→ PlayerStateMachine   校验状态，只上报 .applied
                      ├─→ PlayerTimeModel      节流 + 钳制
                      └─→ AsyncStream<PlayerControllerUpdate>   ← UI 的唯一订阅点
```

**放置位置**：`PlayerCore`（禁止 UI 依赖，故可测；`PlayerUI` 只能作为消费者）。

## 三、`MPVKernel` 缺陷清单（趁 T3 一批改完）

| # | 缺陷 | 位置 | 后果 | 修法 |
| --- | --- | --- | --- | --- |
| a | `attach` 时序是隐式的 | `applyOptions()` 在 `mpv_initialize` **之前**读 `windowEmbedHandle`；nil 时走 `vo=null` / `hwdec=no`（L119-135） | UI 若晚一步 attach ⇒ **画面永远不出来，且零报错** | 收成 `init` 参数或 `load()` 显式校验（同 `P-018` 一类） |
| b | `END_FILE` 不区分错误 | L169-170 无条件 `emit(.stateChanged(.finished))` | 播到坏文件**永远进不了 `.failed`**；`PlayerState.failed` 除 create/init 外是死代码 | 读 `mpv_end_file_reason`；参照 `vendor/ksplayer/Sources/MPVPlayer/KSMPVPlayer.swift` L91-99 |
| c | wakeup 回调 `passUnretained` | L148 | mpv 线程回调与 actor 释放存在竞态 ⇒ use-after-free | `passRetained` + `MPVHandleOwner.deinit` 配对释放（`P-022` 的同一模式） |
| d | `play()` / `pause()` 乐观 emit | L57-67 直接写状态，不观察 mpv | 状态可能与内核不一致；mpv 内部产生的暂停（缓存 / EOF / `keep-open`）UI 收不到 | 改为 observe `pause` 属性；`play/pause` 只发命令（参照 `KSMPVPlayer.swift` L108-111） |

**另外两处**：

| # | 项 | 说明 |
| --- | --- | --- |
| e | `seek` 无精度语义、无钳制 | `seek` 发 `absolute`（默认 keyframe）；钳制应由装配层履行 |
| f | `PlayerKernelSnapshot` 缺 `naturalSize` | 这是**跨层结构**（协议 + `FakeKernel` + 全部测试）。而属性映射正要 observe `width`/`height` ⇒ **必须同批改**，否则返工 |

## 四、两处开放决策（本次拍板，理由如下）

### D-a · `MPV/` 包的门禁策略：**"存在才跑"，不硬失败**

| 选项 | 问题 |
| --- | --- |
| 把 iOS Simulator 构建/测试硬写进门禁 | 自建产物 **104 MB 且被 gitignore** ⇒ 新克隆必然缺失 ⇒ **`./Tools/gate.sh` 必失败**（这正是 `P-021` 一类问题） |
| 完全不进门禁 | 237 行 `MPVKernel` 永远裸奔，`G2` 无自动门 |

**决定**：`Tools/gate.sh` 增加**条件步骤** —— 检测 `MPV/Library/Libmpv.xcframework` 是否存在：

- **存在** ⇒ 跑 `xcodebuild -scheme PlayerMPV -destination 'platform=iOS Simulator' build test`，计入门禁；
- **不存在** ⇒ 打印 `SKIP（产物未 stage，先跑 Tools/stage-libmpv.sh）`，**不计失败**。

同时给 `MPV/Package.swift` 补 `PlayerMPVTests` test target。

### D-b · `seek` 精度：**`absolute+exact`**

**决定**：Phase 2 用 `absolute+exact`。

**理由**：我们的时间模型已经是"节流 + 钳制"，P3 拖拽后若不能精确落点就会"回弹"，那是体验硬伤；exact seek 对本地文件代价很小（从最近关键帧解码）。

**不做的事**：**现在不加"精度模式"参数**。只有 1 个调用方时加模式参数是投机 —— 与"只有一个内核时不做分派"同一口径。直播 / 长 GOP 的 `+keyframes` 留到 `P5`/`P6`，届时再扩 `PlayerKernelProtocol.seek`。

**钳制归属**：钳制是**模型**的职责（`PlayerTimeModel.clampSeekTarget`），由**装配层**调用；内核只负责执行，不重复钳制。

## 七、`G2` 判定口径细化

原口径「本地 mkv 出画 + 出声 + 能 seek」不可执行。细化为**四条同时满足**：

| # | 条件 | 证据形式 |
| --- | --- | --- |
| 1 | 本地 mkv **出画** | 模拟器 + 真机截图（沿用 `docs/assets/` 惯例） |
| 2 | 本地 mkv **出声** | 音频轨枚举正确 + 无 `mpv` 错误日志 |
| 3 | `seek` **落点精确**（`exact`） | 日志：请求目标 vs 实际 `time-pos`，误差 ≤ 1 帧 |
| 4 | `./Tools/gate.sh` **退出 0**（含 `MPV/` 条件步骤） | 脚本输出 |

**多音轨文件**属 `P2-T11` 的验收内容（原票面已写）。
